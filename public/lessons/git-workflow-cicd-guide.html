Section 01

Why Branch Strategy Matters

Without a shared agreement on how code moves through your repository, teams slow down, break things, and lose history. Strategy is the protocol that makes collaboration scale.

⚡ The Problem — No Strategy
Broken builds. Everyone pushes directly to main — one bad commit breaks the whole team's flow.
Messy history. Tangled commits make it impossible to understand what changed and why.
Merge conflicts. Three features developed in parallel collide, and nobody knows who "owns" what.
Slow hotfixes. Production is on fire, but rolling back or patching is dangerous because nothing is isolated.
✦ The Solution — Agreed Strategy
Isolation. Every piece of work lives in its own branch — changes are independent until they're ready.
Quality Gate. MR + code review keeps main always deployable. Nothing lands without passing the bar.
Fast hotfix lane. Critical fixes have a direct, clearly-defined path to production without touching in-progress work.
Clear ownership. Branches map to tasks, tickets, or features — accountability is built into the flow.
Core Insight: A branch strategy is not a Git feature — it's a social contract. The tool is Git; the process saves the team. Strategy complexity should always match team size and deployment frequency.

Key Concepts at a Glance

🔀 Branch

A lightweight, movable pointer to a commit. Creating a branch costs almost nothing in Git — it's just a 41-byte file. Branches let you work in isolation without affecting others.

🔒 Branch Protection

Platform rule that prevents direct pushes to main. Enforces MR + CI green before any merge. This is the cornerstone of production stability.

🚦 CI Gate

Automated checks that must pass before a merge is allowed: lint, build, tests. Turns subjective "should we merge?" into an objective green/red signal.

📦 Commit Convention

Consistent commit messages (Conventional Commits) make history scannable and power automatic changelogs.

🏷️ Semantic Versioning

MAJOR.MINOR.PATCH — a shared language for signalling breaking changes, new features, and bug fixes to every consumer of your software.

🔁 Merge vs Rebase

Merge preserves history as-is. Rebase rewrites commits on top of the target, producing a linear history. Both are valid; your team picks one and sticks to it.

Section 02

Branch Types Deep Dive

Each branch type plays a specific role in the development lifecycle. Understanding when to open which branch — and where to merge it — prevents most collaboration problems.

🚀 Long-lived Branches

main Always production-ready

main / master

Represents production. Every commit here is a potential release. Protected — no direct pushes. Merges happen only via MR after review + CI green. Tagged at each release with a version number.

Protected · Tagged · Deployable
develop Integration branch

develop

The staging area for the next release. Feature branches merge here after review. It may be unstable between feature merges, but is stabilised before release. Used in Git Flow; some teams skip it.

Next release · Unstable OK · Integration

🌿 Feature Branch

Purpose

Temporary branch for a new feature or refactor. Created from develop (Git Flow) or main (GitHub Flow). Lives as long as the feature takes, then merged and deleted.

Naming

feature/login-validation feat/JIRA-42-api feature/payment-form
Always lowercase, hyphen-separated. Include ticket ID when possible.

Best Practice — Keep branches small. A feature branch that lives for 3 days is healthier than one that lives for 3 weeks. Smaller branches = fewer conflicts, faster reviews, easier rollback.
Anti-pattern — "Mega Branch". Accumulating weeks of work in one branch creates a merge nightmare. If a feature is large, break it into sub-tasks, each with its own short-lived branch.
bash # 1. Make sure your base is up to date git checkout develop git pull origin develop # 2. Create and switch to the feature branch git checkout -b feature/payment-form # 3. Work, stage, commit (repeat) git add . git commit -m "feat: add payment form with validation" # 4. Push and open a Merge Request on the platform git push -u origin feature/payment-form # → Open MR: feature/payment-form → develop

🔥 Hotfix Branch

When to use

A critical bug is live in production and cannot wait for the normal release cycle. A hotfix branch lets you patch main directly without dragging along unfinished features from develop.

hotfix/fix-checkout-500 hotfix/auth-token-expiry

Source & Targets

Always branched from main (or the latest production tag). After the fix, merge into both main and develop, so the fix doesn't disappear in the next release.

Hotfix Principles

Minimal change — only the fix, nothing else.
Fast review — on-call engineer or senior reviewer.
Tag immediately — bump patch version, update changelog.

bash # Branch from production git checkout main && git pull git checkout -b hotfix/fix-checkout-500 # Fix, commit, push git commit -am "fix: handle null cart on checkout" git push -u origin hotfix/fix-checkout-500 # After MR → merge to main, then backport to develop git checkout main && git merge hotfix/fix-checkout-500 git tag -a v2.3.1 -m "hotfix: checkout 500 error" git checkout develop && git merge hotfix/fix-checkout-500

📦 Release Branch

Purpose

A release branch freezes develop's state for a specific release version. Only release-related changes go in (version bump, changelog, last-minute bugfixes). While it exists, develop can continue receiving new features for the next sprint.

release/2.4.0 release/v3.0.0-rc1

Lifecycle

1. Branch from develop
2. QA & staging happens here
3. Final bugfixes committed
4. Merge into main + tag
5. Merge back into develop

Semantic Versioning

New feature, backwards-compatible → MINOR

Section 03

Git Flow — The Big Picture

Git Flow is a branching model by Vincent Driessen that defines a strict branching structure. It's one of several popular models — understanding it gives you vocabulary for any workflow discussion.

Hover over any commit node to see its description. Each coloured dot represents a commit; arrows show branch/merge direction. Dashed arrows are back-merges (keeping history in sync).

Git Flow vs GitHub Flow vs Trunk-Based

ModelLong-lived branchesRelease cadenceBest forComplexity
Git Flowmain, developScheduled releasesLibraries, versioned productsHigh
GitHub Flowmain onlyContinuous deploymentWeb apps, SaaS, startupsLow
GitLab Flowmain + env branchesEnv-based deploysMultiple environmentsMedium
Trunk-Basedmain (trunk)Multiple per dayHigh-velocity teams with strong CILow+discipline
Pragmatic advice: Git Flow is the most commonly taught model, but many modern teams use GitHub Flow (feature → MR → main → deploy). Choose complexity that matches your team's size, deployment frequency, and tooling — not the model that sounds most impressive.
Section 04

Merge Requests / Pull Requests

A Merge Request (GitLab) and Pull Request (GitHub) are the same idea: a formal proposal to integrate one branch into another — with built-in discussion, CI results, and review tooling.

📋 What is an MR/PR?

An MR surfaces a diff (line-by-line view of changes), enables threaded discussion, shows CI pipeline results inline, and gates the merge button behind configurable rules (approvals, passing CI, no unresolved threads).

Diff view Inline comments CI status Approval rules Auto-merge

🔄 MR Lifecycle

1. Draft — WIP, feedback welcome but not ready
2. Ready for Review — author marks it ready
3. Review — reviewers comment, request changes
4. Changes Made — author pushes fixes
5. Approved — required approvals granted
6. CI Green — all checks pass
7. Merged — branch integrated, deleted

📝 Writing a Great MR Description

A good description saves reviewers time and creates a permanent record of intent. Treat it like documentation.

markdown ## What I did - Added client-side validation to the login form (email format + required fields) - Extracted validation logic into `useLoginValidation` hook (reusable) ## Why JIRA-42: Prevent empty emails from being submitted to the API. Reduces server error rate and improves UX with instant feedback. ## How I tested it - Manual: empty submit → error messages shown correctly - Manual: invalid email format → error, valid → no error - `yarn test` → all 47 tests pass ## Screenshots [ attach before/after screenshots if UI changed ] ## Notes for reviewer The `useLoginValidation` hook is in `/src/hooks/` — review that file first. I opted for Yup schema over manual checks — see comment in PR for trade-off.

✅ MR Checklist

Click each item to check it off. These are the gates before clicking "Request Review".

FOR THE AUTHOR
  • ✓MR is small — one logical change (avoid 400-line monsters)
  • ✓Clear title and description written — respects reviewer's time
  • ✓Self-reviewed the diff — removed debug logs, leftover TODOs
  • ✓Tests added or updated — CI passes locally
  • ✓Branch is up to date with target (rebase or merge — team convention)
  • ✓No merge conflicts
  • ✓Linked to ticket / issue
FOR THE REVIEWER
  • ✓Responded within 24–48 hours (team SLA)
  • ✓Comments are specific and actionable — not vague
  • ✓Distinguished blocking vs. non-blocking comments clearly
  • ✓Checked correctness and security — not just style
  • ✓Understood the context (ticket/requirements) before reviewing
  • ✓Approved or explicitly requested changes — no ambiguous state

✅ Small MR (<200 lines)

Reviewed in 15–30 min. Conflicts rare. Easy to reason about, easy to revert. Aim for this.

⚠️ Medium MR (200–400 lines)

Acceptable if it's a coherent feature. Needs clear description. Review in under an hour.

❌ Large MR (400+ lines)

"Monster MR". Reviews are superficial — reviewers lose focus. Break it into logical sub-tasks.

Section 05

Code Review Principles

Review is knowledge transfer, not gatekeeping. Both the author and reviewer leave the process having learned something. The goal is improving the codebase — together.

🎯 Code, not personality

Critique the code, never the person. "This function has two responsibilities — consider splitting it" is constructive. "You wrote this poorly" is not. Frame everything around the code's behaviour, not the author's competence.

📏 Priority order

1. Correctness & security — does it do what it should, safely?
2. Maintainability — is it readable and documented?
3. Performance — only when measurable
4. Style — let the linter handle most of this

🧩 Context first

Read the ticket, acceptance criteria, and description before looking at the code. The "perfect" architectural solution may be out of scope for this sprint. Know the constraints before suggesting rewrites.

💡 Review = learning

Junior engineers can catch bugs senior engineers miss — familiarity breeds blindness. Use reviews as a space to share knowledge: "here's an alternative approach" with a link to docs is more valuable than just "fix this".

💬 Comment Quality: Weak vs Strong

❌ Weak Comments
"Fix this."
"I wouldn't do it this way."
"This is wrong."
"????"
"This looks bad."
Problems: vague, no actionable path forward, sounds personal.
✅ Strong Comments
"Add userId to the useEffect dependency array — without it you'll get stale data when the user switches accounts."
"Is server-side validation also in place for this input? Client validation can be bypassed."
"Suggestion (non-blocking): extract a formatPrice helper — this logic appears 3 times."
"This will throw if items is null. Either add a null check or guarantee it upstream."
Good: specific, explains why, proposes a fix, distinguishes blocking vs optional.

🏷️ Comment Labels (Conventional Review Comments)

BLOCKING

Must be resolved before merge. A bug, security issue, or logic error that could ship to production.

SUGGESTION

Non-blocking improvement. The author can accept or decline. Useful for readability, abstractions, naming.

QUESTION

Seeking understanding, not necessarily requiring change. "Why was this approach chosen over X?" Promotes learning.

NITPICK

Minor style issue. Always clearly label nitpicks so authors don't block on them. Auto-fixable with linters ideally.

The golden rule of code review: Review the code you wish someone had reviewed for you. Thorough, kind, specific, educational — not a power trip, not a rubber stamp.
Section 06

CI/CD — Build & Test Pipeline

Continuous Integration and Continuous Delivery/Deployment turn "it works on my machine" into "it works, and we can prove it." The pipeline is your automated quality gate.

🔄 CI — Continuous Integration

Code is merged often (ideally daily). Every push or MR triggers an automated build and test run. The goal: catch integration bugs immediately, not weeks later.

📦 CD — Continuous Delivery

Every successful CI run produces an artifact that is ready to deploy at any time. The actual deploy to production is manual — a human makes the final decision.

🚢 CD — Continuous Deployment

The next level: if all tests pass, the deployment to production is automatic. Requires strong monitoring, feature flags, and rollback capability. Used by mature teams.

📄 GitHub Actions — Real Example

This is a production-quality workflow file. Every keyword explained inline.

yaml name: CI Pipeline # Triggers: runs on every MR targeting main, and on pushes to main on: pull_request: branches: [main, develop] push: branches: [main] jobs: build-and-test: runs-on: ubuntu-latest # fresh Ubuntu VM per run strategy: matrix: node-version: [20, 22] # test against multiple Node versions steps: - uses: actions/checkout@v4 # pull the code - uses: actions/setup-node@v4 with: node-version: '${{ matrix.node-version }}' cache: 'npm' # cache node_modules between runs - run: npm ci # clean install (respects package-lock) - run: npm run lint # ESLint / Prettier check - run: npm run build # TypeScript compile + bundle - run: npm test -- --coverage # tests + coverage report security: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Run Snyk security scan uses: snyk/actions/node@master env: SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}

🧪 Why Tests Must Live in CI

Eliminates "works on my machine"

CI runs in a clean, reproducible environment. Missing env variables, incorrect Node versions, missing global tools — all surface in CI, not in production.

Regression protection

Every MR that touches the codebase re-runs the full test suite. A change in module A that silently breaks module B gets caught immediately — not after the code ships.

Objective merge gate

"The CI is red" is an undeniable, objective fact. It removes personality from the merge decision — you can't argue with a failed test, only fix it.

Realistic expectations

100% coverage is not always the goal — pursue meaningful tests. Watch out for flaky tests (intermittent failures) — they erode trust in the pipeline. Fix or delete them aggressively.

Progressive CI: Start with lint + build. Add unit tests. Then integration tests. Then security scans, coverage thresholds, performance budgets. Build your pipeline incrementally — a pipeline that runs in 3 minutes and always passes is more valuable than a 20-minute suite nobody trusts.
