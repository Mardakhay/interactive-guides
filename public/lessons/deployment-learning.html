01 / Introduction

Why Deployment Matters

You can write the most beautiful React app in the world — but if it only runs on your localhost:5173, nobody can see it. Deployment is the bridge between your local development environment and the real internet.

🎯 Portfolio & Interviews

Recruiters and interviewers expect a live link. A GitHub repo alone is rarely enough — they want to click and see it work.

🐛 Production Bugs

Problems like CORS errors, wrong API URLs, missing env vars only surface in production. You need to discover and fix them early.

👥 Team Collaboration

Preview deployments let teammates, mentors, and clients review changes before they go live — no "it works on my machine."

⚡ Modern Workflow

Push → Deploy is the industry standard. Code merges automatically trigger deployments — no manual FTP uploads.

🎯 Three goals of modern deployment
▶

1. Auto-deploy (Push → Live) — Every push to main automatically rebuilds and deploys. No manual steps.

2. Preview deployments — Every Pull Request gets a unique URL, so you can review changes before merging.

3. Rollback — If a bad deploy makes it to production, you can revert to a previous snapshot in 30 seconds without re-building.

02 / Build Process

Development vs Production

Toggle to compare the two modes

🛠 Development Mode — npm run dev

  • ⚡ Vite Dev Server — Extremely fast startup, serves files directly from source
  • 🔄 HMR (Hot Module Replacement) — Changes appear in browser without full reload
  • 📖 No minification — Code stays readable, easy to debug
  • 🗺 Source maps active — DevTools shows your real file names and line numbers
  • 🐛 Verbose errors — React dev mode, detailed warnings

📦 Production Mode — npm run build

  • 🗜 Minification — Whitespace removed, variable names shortened, file sizes shrink 70-80%
  • 🌳 Tree-shaking — Unused imports/functions are automatically removed
  • ✂️ Code splitting — App split into chunks, loaded on demand (lazy loading)
  • 🔑 Content hashing — File names include hash for cache busting
  • 📁 Output: dist/ — Static files ready to serve from any CDN

03 / Output

The dist/ Folder

After running npm run build, Vite creates a dist/ directory containing fully static, production-ready files. This is what Vercel or Netlify actually serves to your users.

dist/
├── index.html ← entry point, ~2KB
├── assets/
│ ├── index-[8fk2j9a].js ← main JS bundle
│ ├── index-[3dc8e1f].css ← compiled styles
│ ├── vendor-[9ab3c7d].js ← third-party libs
│ └── logo-[5ef1b2c].svg ← hashed static assets
└── favicon.ico

🔑 Content Hashing — Why those weird filenames?

The hash in filenames (e.g. index-8fk2j9a.js) changes every time the file's contents change. This enables aggressive browser caching: unchanged files are served from cache, changed files get new names so users always see the latest version.

🚨
Never commit dist/ to Git

The dist/ folder is generated output. Add it to .gitignore. Vercel and Netlify will build it themselves during deployment.

🌳 What is Tree-shaking exactly?
▶

Tree-shaking is a form of dead code elimination. If you import {'{'} something {'}'} from 'lodash' but never use something, the build tool removes it entirely. Your final bundle only contains code that is actually executed.

This is why modern bundlers (Vite, Rollup, Webpack) prefer ES Modules (import/export) over CommonJS (require) — static imports can be analyzed at build time.

✂️ What is Code Splitting?
▶

Instead of sending your entire app in one giant JS file, code splitting breaks it into smaller chunks. Pages or heavy components loaded with React.lazy() become separate files — the user only downloads them when needed.

LazyRoute.jsx 
// This creates a separate chunk — only loaded on /dashboard
const Dashboard = React.lazy(() => import('./pages/Dashboard'));

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <Route path="/dashboard" element={<Dashboard />} />
    </Suspense>
  );
}

04 / Configuration

Environment Variables

Environment variables are values stored outside your code that change depending on the environment (development, staging, production). They keep sensitive information out of your codebase.

🔑 Common Examples

  • • VITE_API_URL — backend endpoint
  • • VITE_STRIPE_KEY — payment public key
  • • VITE_FIREBASE_KEY — Firebase config
  • • VITE_FEATURE_DARK_MODE — feature flags

💡 Why Not Just Hardcode?

  • 🔒 Secrets must not appear in Git
  • 🌍 Different URL per environment
  • 👥 Each developer has own local values
  • 🔄 Change config without changing code
⚠️
Frontend env vars are NOT secret

Any variable exposed to the browser (prefixed with VITE_) gets bundled into the JavaScript file and is readable in DevTools → Sources. Never put private keys, passwords, or database URLs in VITE_ variables. Those belong on your backend only.

✅ Frontend (Public)
VITE_API_URL
VITE_PUBLIC_KEY
VITE_APP_TITLE
→
🚨 Backend Only (Secret)
DATABASE_URL
SECRET_KEY
STRIPE_SECRET
.env 
# ✅ Safe — VITE_ prefix exposes to browser bundle
VITE_API_URL=https://api.example.com
VITE_APP_TITLE=My Dashboard
VITE_FEATURE_DARK_MODE=true

# 🚨 NEVER in frontend .env — backend only!
DATABASE_URL=postgres://user:pass@host/db
SECRET_KEY=super-secret-abc123
STRIPE_SECRET_KEY=sk_live_...
Using env vars in your code 
// Read in any Vite component or utility file
const apiUrl  = import.meta.env.VITE_API_URL;
const title   = import.meta.env.VITE_APP_TITLE;

// Built-in Vite booleans (no VITE_ prefix needed)
const isDev   = import.meta.env.DEV;    // true in dev
const isProd  = import.meta.env.PROD;   // true in prod
const mode    = import.meta.env.MODE;   // "development" | "production"

// Usage in fetch
const res = await fetch(`${import.meta.env.VITE_API_URL}/users`);

// Conditional logic based on environment
if (import.meta.env.DEV) {
  console.log('Debug info — dev only');
}
src/vite-env.d.ts — TypeScript support 
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_APP_TITLE: string;
  readonly VITE_FEATURE_DARK_MODE: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

// Now import.meta.env.VITE_API_URL has autocomplete ✨

05 / .env Files

.env Files & Priority

Vite loads different .env files depending on the current mode. Understanding the priority order helps you avoid hard-to-debug issues where the wrong value is being used.

.env.local .env.local Highest priority · Personal, never committed to Git ▶
Your personal overrides. This file is in .gitignore by default. Use it for your own API keys during development. It overrides everything else. Never share or commit this file.
.env.development.local .env.development.local Dev-mode personal overrides (not committed) ▶
Same as .env.local but only loaded when running npm run dev. Useful if you need to override dev-specific values on your machine.
.env.development .env.development Loaded only during npm run dev · Can be committed ▶
Shared dev config that your whole team uses. Safe to commit. Example: point the API URL to a staging server that all developers use.
.env.production .env.production Loaded during npm run build · Production values ▶
Used at build time when deploying. Can be committed since it should only contain non-secret production config. Platform env vars (Vercel/Netlify) override these at build time.
.env .env Lowest priority · Loaded in all modes · Default values ▶
The base/default config file. Loaded in every mode. Put non-sensitive defaults here. All other files override these values when they define the same key.

gitignore & .env.example Pattern

.gitignore 
# Environment variables — NEVER commit these
.env
.env.local
.env.*.local

# Build output
dist/
build/

# Dependencies
node_modules/
.env.example — ✅ Commit this file 
# Copy this file to .env.local and fill in your values
# cp .env.example .env.local

VITE_API_URL=
VITE_APP_TITLE=
VITE_FEATURE_DARK_MODE=
🚨
If .env lands in Git history, treat it as compromised

Even one accidental commit exposes your keys. Rotate all API keys immediately. Use git filter-repo to scrub history. Prevention is far easier than cleanup.

08 / Routing

SPA Routing Problem

This is one of the most common "it worked locally but broke in production" issues for React developers. Understanding it once will save you hours.

❌ Without _redirects — What breaks

User types: /about
→
Browser requests /about from server
↓
Server looks for about.html → not found
→
404 Error ❌

✅ With _redirects — Correct behavior

User types: /about
→
Server redirects all routes → index.html
↓
React Router handles /about client-side
→
About page renders ✅
🧠 Why does this happen? (the deep explanation)
▶

In a traditional website, every URL corresponds to a physical file on the server — /about maps to about.html. Your server finds the file and sends it.

In a React SPA, there is only one real file: index.html. React Router then intercepts the URL and renders the correct component client-side. This works perfectly when navigating within the app.

The problem: if a user refreshes the page on /about, the browser asks the server for /about — the server has no such file, returns 404. The _redirects rule says "send index.html for every path instead" so React gets to boot up and handle routing.

↩️ Rollback — Your Safety Net

Every deploy is saved as a snapshot. If a bad deploy goes to production:

VERCEL

Deployments → find the good version → "···" → "Promote to Production"

NETLIFY

Deploys → find the good version → "Publish deploy"

⚡
Rollback doesn't rebuild

It activates a previously built snapshot. That's why it's nearly instant — no re-running npm run build.

⚠️ Most Common Deployment Mistakes

🔑 Forgot to add env vars to the platform
▶

Your .env.local file is on your machine, not in Git. The platform has no idea what VITE_API_URL is unless you explicitly add it in Settings → Environment Variables. Always do this before your first deploy.

🔄 Changed env var but didn't redeploy
▶

Environment variables are embedded in your bundle at build time, not runtime. If you update a value in the platform dashboard, you must trigger a new deployment for it to take effect. Go to Deployments → Redeploy.

🔀 Missing _redirects on Netlify
▶

The most common React-on-Netlify bug. Create public/_redirects with the content /* /index.html 200. The public/ folder is copied as-is to dist/ during build, so the file will exist at the root of your deployment.

🔗 API URLs still pointing to localhost
▶

If you hardcoded http://localhost:3000 instead of using import.meta.env.VITE_API_URL, your production app will try to call localhost — which doesn't exist on a user's browser. Always use env vars for URLs.
