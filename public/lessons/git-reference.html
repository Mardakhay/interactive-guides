What is Git?

Git is software that allows you to track changes made to a project over time. It records changes, stores them, and lets you reference them as needed — like a time machine for your code.

📁

Working Directory

Where you create, edit, delete, and organize files. This is your active workspace where all changes begin.

📋

Staging Area

Where you list changes from the working directory that you want to save. A preparation zone before committing.

🏛️

Repository

Where Git permanently stores changes as different versions of the project. Your project's entire history lives here.

Basic Workflow

The standard Git cycle: edit → stage → commit. Every version in your project's history follows this pattern.

Key Operations

Undo mistakes, manage your HEAD, stash in-progress work, and amend commits — the power tools of Git.

👁️

HEAD Commit

▼

The HEAD commit is the commit you are currently on — usually the most recently made commit.

BASH
$ git show HEAD
# Shows git log info + all file changes for HEAD commit
↩️

Reverting Changes

▼

Discard changes in a file and revert to the last committed state:

BASH
$ git checkout HEAD filename
# Resets file to its state at the last commit
🗑️

Unstaging a File

▼

Remove a file from staging without discarding your working directory changes:

BASH
$ git reset HEAD filename
# Unstages file, keeps working directory changes intact
⏪

Rewind to Previous Commit

▼

Move HEAD back to a specific previous commit using its SHA:

BASH
$ git reset 5d69206
# Use first 7 characters of the commit SHA
📦

Git Stash

▼

Temporarily save in-progress work when you need to switch branches without committing:

BASH
$ git stash     # Save changes to hidden directory
$ git stash pop # Restore stashed changes
✏️

Amend Last Commit

▼

Correct or update the last commit with new staged changes:

BASH
$ git add <files>
$ git commit --amend
$ git commit --amend --no-edit # Keep same message
⚡

Git Aliases

▼

Create shortcuts for long Git commands to speed up your workflow:

BASH
$ git config --global alias.co "checkout"
# Now use: git co branch_name

Git Branching

Branches let you experiment with different versions of a project. Changes on a branch don't affect master until you merge.

🌿

New Features

Develop features in isolation without breaking the stable main branch.

🐛

Bug Fixes

Fix bugs on a dedicated branch, test it, then merge when ready.

🧪

Experiments

Try risky ideas freely — if they don't work, just delete the branch.

BASH — BRANCH COMMANDS
$ git branch                        # See current branch
$ git branch new_branch            # Create branch
$ git checkout branch_name         # Switch to branch
$ git merge branch_name            # Merge into current
$ git branch -d branch_name        # Delete branch

⚠️ Merge Conflicts

If both master and the branch have changes, Git may encounter a merge conflict. This happens when Git cannot automatically decide which changes to keep. You'll need to manually resolve conflicts in the affected files.

💡 Branch naming tips: Use descriptive names (feature/login, fix/navbar-bug). No whitespace allowed. Branches are a means to an end — create, work, merge, delete.

Intro to GitHub

GitHub is a website and service that facilitates software development by storing code in repositories and tracking changes. It uses Git for version control and provides hosting, testing, and deployment tools.

🖥️

Git (Local)

A version-control system maintained on your local machine. Tracks history, creates branches, and manages commits offline.

🐙

GitHub (Remote)

A hosting service for Git repositories. Enables collaboration, code reviews, pull requests, and deployment.

Git Teamwork

Git provides tools for collaboration using remotes — shared Git repositories that let collaborators work independently and merge changes when ready.

BASH — CLONE & REMOTE
$ git clone remote_location clone_name
# Git auto-names the remote "origin"

$ git remote -v   # View remotes
BASH — FETCH & MERGE
$ git fetch                     # Fetch updates (no merge)
$ git merge origin/master       # Merge remote → local
$ git push origin your_branch   # Push your branch

Typical Collaboration Workflow

1
Fetch and merge changes from the remote repository
2
Create a branch for a new feature
3
Develop and commit your work on the branch
4
Fetch and merge again to prevent conflicts before pushing
5
Push your branch to the remote for team review

GitHub Markdown

Markdown gives your GitHub repositories better readability. It converts a lightweight syntax to HTML — headings, lists, code blocks, and more. Faster and simpler than writing HTML directly.

📌

Headers

▼
MARKDOWN
# H1 — first level heading
## H2 — second level
### H3 — third level
#### H4 — and so on...
📋

Lists

▼

Create bulleted lists with *, +, or -. Numbered lists with 1., 2., etc.

MARKDOWN

📄

README Files

▼

A good README is the front page of your repository. Include:

  • Project Title
  • Description — purpose, motivation, what problem it solves
  • Features — screenshots or GIFs of unique features
  • How to Use — installation and usage instructions
  • Technologies — frameworks and tools used
  • Collaborators — credit contributors with GitHub links
  • License — define usage permissions

README files use the .md extension and are automatically parsed by GitHub.

GitHub Pages

GitHub Pages is a free service that lets you deploy static websites to the public Internet. Every push to your repository automatically updates your live site.

BASH — DEPLOY TO GITHUB PAGES
# 1. Clone repo named username.github.io
$ git clone https://github.com/username/username.github.io

# 2. Enter project folder
$ cd username.github.io

# 3. Create your index.html
$ echo "Hello World" > index.html

# 4. Commit and push
$ git add --all
$ git commit -m "Initial commit"
$ git push -u origin main

Pull Requests

A pull request (PR) lets you review code before merging it from one branch into main. It's the core collaboration feature of GitHub.

📝

Clear Title & Description

Explain your thought process, options considered, and decisions made. Add screenshots or videos when helpful.

📦

Keep PRs Small

Smaller PRs are easier and faster to review. Break large features into smaller, logical chunks.

✅

Use Templates

Checklists ensure all relevant info is included. Structured PRs reduce back-and-forth.

💬

Clear Commit Messages

Good commit messages help reviewers understand the history. Add code comments where needed.

⚡

Respond Promptly

Quick responses to feedback keep momentum. Aim for fast merges to avoid long-lived branches.

🔍

Line-by-line Review

GitHub enables focused discussion on specific lines of code within a PR.

Git Rebase

Git Rebase changes a branch's starting point, making it seem as if the branch began from a later commit. Useful for keeping feature branches up to date and maintaining a clean history.

Git Merge Git Rebase
Combines branch histories with a merge commit Reapplies commits on top of another branch
Preserves original history Creates a linear, cleaner history
Maintains accurate historical record Simplifies commit graph for readability

⚠️ Rebase Drawbacks

  • •Rewrites history — can complicate tracking. Best for local branches only.
  • •More merge conflicts — requires resolving conflicts more often.
  • •Avoid on shared branches — can desynchronize collaborator history.

.gitignore

A .gitignore file keeps unwanted or sensitive files out of commits. Place it at the root of your project.

.GITIGNORE — EXAMPLE
# Dependencies
node_modules/

# Build output
build/
dist/

# Environment variables (SENSITIVE!)
.env
.env.local

# Wildcards
*.log

# NOT ignore (! prefix)
!important.log
🧹

Keeps Repo Clean

Helps teams focus on meaningful changes only.

🔒

Protects Secrets

Keeps API keys, passwords, and environment files out of version control.

🚀

Better Efficiency

Ensures builds and deployments only include necessary files.
