Chapter 01

What Is a Design System?

A Design System is a centralized collection of reusable components, standards, and guidelines that act as the single source of truth across an entire product organization. Think of it as the architectural rulebook for your UI.

💡
Analogy: A Design System is like a city's architectural code — every building is different, but there's a shared visual language. Roads are the same width, signage follows standards, and buildings speak the same design dialect.
The Core Formula
Components + Rules + Styles = Design System
🔁
Consistency
Every button, input, and modal looks and behaves identically across the entire product — on every screen, every platform.
⚡
Speed
Developers grab pre-built, tested components instead of reinventing the wheel on each feature. Ship 3× faster.
🗣
Shared Language
Designers and developers stop miscommunicating. "Primary button large" means exactly one thing to everyone on the team.
📈
Scalability
As your product grows to dozens of teams, a DS keeps everything from diverging into chaos. Structure at any scale.

Chapter 02

Design System Structure

Design systems are typically built in layers — a hierarchy inspired by chemistry. This methodology is called Atomic Design, coined by Brad Frost.

⚗️
Atomic Design Philosophy: Just as chemistry builds molecules from atoms and organisms from molecules, UI systems build complex screens from tiny, primitive pieces. Each level encapsulates the one below it.
The Layer Hierarchy
🎨
Tokens
Colors, spacing, fonts, shadows
→
🧱
Atoms
Button, Input, Badge, Icon
→
🧩
Molecules
Card, SearchBar, Form
→
🦠
Organisms
Header, Sidebar, DataTable
→
📄
Pages
Dashboard, Profile, Checkout
🧱 Atoms
The smallest possible UI units. Cannot be broken down further without losing meaning. Examples: a single button, an icon, a label. Each atom has one purpose only.
🧩 Molecules
Two or more atoms working together as a unit. A search bar = Input atom + Button atom. A form field = Label + Input + Error message atoms.
🦠 Organisms
Complete, standalone UI sections that combine multiple molecules. A navigation header, a product card grid, a comment thread. These are recognizable interface regions.
⚠️
Common mistake: Don't skip levels. If you're building a complex page component before you have stable atoms, you'll create brittle code that's hard to maintain. Build bottom-up.
Chapter 03

Design Tokens

Design tokens are the DNA of a design system — named variables that store every visual decision. Instead of hardcoding #3b82f6, you use a named token like colors.primary.500.

Why Tokens?
  • Centralized changes — Update a color in one place, it applies everywhere automatically
  • Dark Mode — Swap token values, not hunt through thousands of hardcoded hex values
  • Theming — Multiple brand themes from the same component library
  • Designer-Developer sync — Figma tokens map 1:1 to code tokens
  • Semantic meaning — color.danger communicates intent; #ef4444 does not

Chapter 05

Build vs Buy

One of the most critical decisions in frontend architecture: should you use an existing UI library, or build your own design system from scratch?

✅ Use an Existing Library When...
  • You're building an MVP and time-to-market matters
  • Small team with limited design resources
  • Standard admin panel or dashboard
  • Accessibility compliance is required immediately
  • The library's aesthetic matches your brand closely
🛠 Build Your Own When...
  • You have a unique, distinctive brand identity
  • Bundle size is critical (libraries are heavy)
  • You need total control over every pixel
  • Your components are simple and stable
  • You have design system engineers on the team
💡
Pragmatic advice: Start with a library for speed, then gradually replace components with custom ones as your brand and requirements crystallize. You don't have to choose all-or-nothing.
Chapter 06

Component Design Principles

Every great UI component follows a set of battle-tested design principles. These rules make your components predictable, maintainable, and a joy to use.

🎯
Single Responsibility
Each component does exactly one thing well. A Button is for triggering actions. An Input is for text entry. Never combine responsibilities in one component.
🔌
Open for Extension
Components must accept className, style, and ...rest so consumers can extend behavior without modifying the source.
📐
Composition over Config
Prefer children composition over a wall of props. <Card.Header> is more flexible than title="...".
♿
Accessibility First
Semantic HTML, ARIA labels, keyboard navigation, and focus management should be built in — not bolted on after the fact.
📖
Self-Documenting API
Prop names should communicate intent: variant="danger" is immediately clear. Avoid cryptic props like type={3}.
🔒
Type Safety
TypeScript interfaces + union types catch errors at compile time. If it can't be misspelled or misused, your component is safer to consume.
❌ Bad: Too many responsibilities
// Anti-pattern: "God component"
<SuperComponent
  type="button"
  mode="fancy"
  showModal={true}
  fetchData={apiCall}
  renderChart={true}
/>
✅ Good: Each does one job
// Separate components, clear purpose
<Button onClick={openModal}>Open</Button>
<Modal open={isOpen}>
  <DataTable data={rows} />
  <Chart data={chartData} />
</Modal>

Chapter 08

Button Component — Full Implementation

Let's build a production-grade Button component from scratch — covering the TypeScript interface, class generation logic, CSS architecture, and edge cases.

components/ui/Button.tsx
import React from 'react';
import './Button.css';

type ButtonVariant = 'primary' | 'secondary' | 'danger' | 'ghost';
type ButtonSize = 'sm' | 'md' | 'lg';

interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: ButtonVariant;
  size?: ButtonSize;
  loading?: boolean;
  fullWidth?: boolean;
  leftIcon?: React.ReactNode;
  rightIcon?: React.ReactNode;
}

function Button({
  variant = 'primary',
  size = 'md',
  loading = false,
  fullWidth = false,
  leftIcon,
  rightIcon,
  children,
  className = '',
  disabled,
  ...rest
}: ButtonProps) {
  // Build class string from props
  const classes = [
    'btn',
    `btn--${variant}`,
    `btn--${size}`,
    fullWidth ? 'btn--full' : '',
    loading  ? 'btn--loading' : '',
    className,
  ].filter(Boolean).join(' ');

  return (
    <button
      className={classes}
      disabled={disabled || loading}
      aria-busy={loading}
      {...rest}
    >
      {loading && <span className="btn__spinner" aria-hidden />}
      {leftIcon && <span className="btn__icon">{leftIcon}</span>}
      <span className="btn__text">{children}</span>
      {rightIcon && <span className="btn__icon">{rightIcon}</span>}
    </button>
  );
}

export default Button;

Input Component

A truly reusable Input wraps much more than an <input> tag — it handles labels, error messages, helper text, icons, variants, and accessibility all in one component.

// Default state
This is helper text
// Error state
⚠ Please enter a valid email address
components/ui/Input.tsx
import React from 'react';

type InputVariant = 'outlined' | 'filled' | 'standard';

interface InputProps
  extends React.InputHTMLAttributes<HTMLInputElement> {
  label?: string;
  error?: string;        // Error message string
  helperText?: string;   // Hint text below input
  variant?: InputVariant;
  leftIcon?: React.ReactNode;
  fullWidth?: boolean;
}

function Input({
  label, error, helperText,
  variant = 'outlined',
  leftIcon, fullWidth = false,
  className = '', id, ...rest
}: InputProps) {
  // Auto-generate id from label for a11y
  const inputId = id || `input-${label?.toLowerCase().replace(/\s+/g, '-')}`;

  return (
    <div className={[
      'input-wrapper',
      fullWidth && 'input--full',
      error    && 'input--error',
      className
    ].filter(Boolean).join(' ')}>

      {label && (
        <label htmlFor={inputId} className="input__label">
          {label}
        </label>
      )}

      <div className={`input__field input--${variant}`}>
        {leftIcon && <span className="input__icon">{leftIcon}</span>}
        <input
          id={inputId}
          aria-invalid={!!error}
          aria-describedby={error ? `${inputId}-error` : undefined}
          {...rest}
        />
      </div>

      {error && (
        <span id={`${inputId}-error`} className="input__error" role="alert">
          ⚠ {error}
        </span>
      )}
      {helperText && !error && (
        <span className="input__helper">{helperText}</span>
      )}
    </div>
  );
}

export default Input;
♿
Accessibility note: Notice aria-invalid, aria-describedby, and role="alert" — these ensure screen readers announce error states correctly. The htmlFor links the label to the input so clicking the label focuses the field.
Chapter 10

Card Component

The Card component demonstrates the Compound Component Pattern — where sub-components like Card.Header, Card.Body, and Card.Footer compose naturally.

📦 Elevated Card
Shadowed, default variant. Used for primary content areas and interactive cards.
📋 Outlined Card
Border only, no fill. Ideal for listing items with visual separation.
🎨 Filled Card
Subtle background tint. Useful for highlighting sections or status areas.
components/ui/Card.tsx — Compound Component
type CardVariant = 'elevated' | 'outlined' | 'filled';

interface CardProps {
  variant?: CardVariant;
  hoverable?: boolean;
  clickable?: boolean;
  padding?: 'sm' | 'md' | 'lg';
  children: React.ReactNode;
  onClick?: () => void;
}

function Card({ variant = 'elevated', hoverable, clickable,
  padding = 'md', children, onClick }: CardProps) {
  return (
    <div
      className={['card',`card--${variant}`,`card--pad-${padding}`,
        hoverable && 'card--hoverable',
        clickable && 'card--clickable'
      ].filter(Boolean).join(' ')}
      onClick={onClick}
      role={clickable ? 'button' : undefined}
    >
      {children}
    </div>
  );
}

// Attach sub-components as static properties
Card.Header = ({ children, className = '' }) => (
  <div className={`card__header ${className}`}>{children}</div>
);

Card.Body = ({ children, className = '' }) => (
  <div className={`card__body ${className}`}>{children}</div>
);

Card.Footer = ({ children, className = '' }) => (
  <div className={`card__footer ${className}`}>{children}</div>
);

export default Card;

// Usage — reads naturally like HTML:
<Card variant="elevated" hoverable>
  <Card.Header>👤 User Profile</Card.Header>
  <Card.Body>
    <p>Name: Amir Hasanov</p>
    <p>Role: Frontend Developer</p>
  </Card.Body>
  <Card.Footer>
    <Button variant="ghost">Cancel</Button>
    <Button>Save Profile</Button>
  </Card.Footer>
</Card>
Chapter 11

Advanced Patterns

Three powerful patterns every serious React component library must master: Compound Components, forwardRef, and Polymorphic components.

① Compound Component Pattern
Think of <select> + <option> — they only make sense together. This pattern lets parent and child components share implicit state without prop drilling.
Accordion — Compound Pattern
// Context for shared state between compounds
const AccordionCtx = createContext({});

function Accordion({ children }) {
  const [open, setOpen] = useState(null);
  return (
    <AccordionCtx.Provider value={{ open, setOpen }}>
      <div className="accordion">{children}</div>
    </AccordionCtx.Provider>
  );
}

Accordion.Item = ({ id, title, children }) => {
  const { open, setOpen } = useContext(AccordionCtx);
  const isOpen = open === id;
  return (
    <div>
      <button onClick={() => setOpen(isOpen ? null : id)}>
        {title} {isOpen ? '▲' : '▼'}
      </button>
      {isOpen && <div>{children}</div>}
    </div>
  );
};

// Clean consumer API:
<Accordion>
  <Accordion.Item id="1" title="What is React?">...</Accordion.Item>
  <Accordion.Item id="2" title="What are hooks?">...</Accordion.Item>
</Accordion>
② forwardRef Pattern
By default, you cannot attach a ref to a custom component. forwardRef passes the ref through to the underlying DOM element — essential for focus management, animations, and form libraries.
❌ Without forwardRef
// ref is lost! React warns you.
const emailRef = useRef(null);

// This ref won't attach
<Input ref={emailRef} />

// Warning: Function components
// cannot be given refs.
✅ With forwardRef
const Input = forwardRef<
  HTMLInputElement, InputProps
>((props, ref) => (
  <input ref={ref} {...props} />
));

// Now this works!
emailRef.current?.focus();
emailRef.current?.select();
③ Polymorphic "as" Pattern
The as prop lets a component render as any HTML element or React component — keeping styles while changing semantics. A Button can become an <a> tag or a React Router <Link>.
Polymorphic Button
interface PolymorphicProps {
  as?: React.ElementType;  // 'button' | 'a' | Link | div | ...
}

function Button({
  as: Component = 'button',
  variant = 'primary',
  children,
  ...rest
}: ButtonProps & PolymorphicProps) {
  return (
    <Component
      className={`btn btn--${variant}`}
      {...rest}
    >
      {children}
    </Component>
  );
}

// Three ways to use the same component:
<Button onClick={save}>Save Changes</Button>      // <button>
<Button as="a" href="/docs">Read Docs</Button>    // <a href>
<Button as={Link} to="/dashboard">Go Home</Button> // React Router
