Stack Memory

The stack is a useful model for understanding nested function calls: the most recent call returns first. This is called LIFO (Last In, First Out). A stack diagram helps explain call frames, but ECMAScript does not require every local variable or primitive value to occupy a particular physical stack slot.


Think of active calls and temporary execution state as stack-like in this model. The exact representation of variables and values is engine-dependent and may change with optimization.

⚡ Why is Stack so fast?

A native call stack can often manage frames efficiently by adjusting a stack pointer. That is a low-level implementation model, not a promise that every JavaScript binding is stored there or that every JavaScript operation has a fixed cost. Engines may optimize or represent values differently.

📏 Fixed Size Matters

JavaScript values do not have a portable, source-level byte size. A number or boolean cannot be used to infer a physical stack layout, and JavaScript is not generally compiled with every local value assigned a fixed stack slot. Representation depends on the engine, runtime state and optimizations.

📚
Analogy: A stack of books on a desk. You can only add or remove from the top. When a function is called, a new "book" (frame) is added. When the function ends, that book is removed. It's fast because you always know exactly where the top is.

Heap Memory

The heap is a useful model for dynamically allocated data such as objects, arrays and closures. These values may outlive the function that created them when other code still references them. The model does not expose an object’s physical address, and the JavaScript specification does not mandate a particular stack/heap layout.

🗃️ Why does Heap exist?

Objects and arrays can have dynamic shapes or sizes, so engines need memory-management strategies beyond a simple fixed-size call frame. It is not correct to conclude that every object must occupy a particular heap layout or that the engine can never keep a value elsewhere; those are implementation details.

🔗 References not values

When you assign an object to another variable, the variable receives the object value (a reference to the same object), not a deep clone. Diagrams often draw that reference as an arrow to a heap object, but JavaScript does not expose a portable numeric memory address or guarantee that exact physical layout.

🐢 Why is Heap slower?

Allocation, object access and garbage collection have implementation- and workload-dependent costs. Fragmentation and collection work can matter in some runtimes, but there is no universal rule that every heap access is slower than every stack access. Diagnose performance with measurements rather than this picture alone.

💥 Fragmentation

Some allocators can experience fragmentation, but the exact allocation strategy and its costs depend on the runtime and workload. This is a conceptual illustration, not a description of every JavaScript engine’s garbage collector or allocator.

🏭
Analogy: A warehouse with shelf tickets. When you put a box (object) in the warehouse, you get a ticket (reference/address). Your desk (stack) holds only the ticket, not the whole box. If someone else needs the same box, they get a copy of the ticket — not another copy of the box.

The Call Stack

The call stack is a model of nested function calls and their return order. Each call may add a frame; returning unwinds the active call sequence. The idea is useful for tracing recursion and stack overflow.


The exact contents of an engine’s frame (locals, arguments, return metadata, optimized values) are implementation details and may differ when the engine optimizes code.

💥 Stack Overflow

If functions keep calling each other endlessly (recursion without a base case), the call stack eventually runs out of space. This causes a Stack Overflow error. The threshold varies by engine, host, code shape and runtime conditions; do not rely on a fixed number of frames.

🌍 Execution Context

Every time JavaScript runs, it creates an Execution Context — a container that holds all the information needed to run a piece of code. There are two types:

🌐 Global Execution Context

Created according to the script/module and host environment. Browser and Node.js globals differ; globalThis is the portable way to refer to the global object where supported. Do not treat the global execution context as a guaranteed, permanently visible bottom frame in a physical call-stack diagram.

📦 Function Execution Context

Created every time a function is called. Contains: the function's own variables (Variable Environment), the scope chain to look up outer variables, and the value of this.

🔗 Scope Chain

Variable lookup follows lexical scope from the current environment outward. A function’s lexical relationships come from where it is defined; a closure lets a function continue to access the outer bindings it needs after the outer call has returned.

Primitives vs Non-Primitives

Primitive types: number, string, boolean, undefined, null, symbol and BigInt are copied by value.

Objects: when you assign an object value to another variable or pass it to a function, both bindings can refer to the same object. This explains aliasing and mutation; it does not mean JavaScript exposes pointers or mandates that primitives and objects live in particular physical memory regions.

When you copy a primitive, you get a completely independent copy. Changing one does NOT affect the other.

Why does object mutation matter?

Because multiple variables can point to the same heap object, changing a property through one variable affects all variables pointing to it. This is a common source of bugs for JS newcomers.

const user = { name: "Alice" }; // Object in heap const admin = user; // admin points to SAME object admin.name = "Bob"; // mutate via admin console.log(user.name); // "Bob" !! user is affected too // Because user and admin point to the SAME memory address

Shallow Copy vs Deep Copy

To avoid the shared-reference problem, you need to copy an object. But there are two kinds of copies, and they behave very differently with nested objects.

📄 Shallow Copy

Copies only the top level properties. Nested objects are still shared by reference. Methods: Object.assign(), spread {...obj}.

📚 Deep Copy

A deep clone separates nested object identity for the data types it supports. structuredClone() supports more values and cycles than JSON serialization, but it still has limits. JSON.parse(JSON.stringify()) is lossy for values such as undefined, functions and symbols, and it fails on cycles. Choose a method for the actual data shape.

The Truth About const

const prevents reassignment of the binding; it does not deep-freeze an object. Primitive values themselves are immutable, but that is a property of JavaScript’s primitive values—not an extra freeze performed by const. An object bound with const can still have mutable properties unless separately protected.

📌
Analogy: const is like a pinned label on a mailbox. You can't point that label at a different mailbox. But you can absolutely change what's inside the mailbox. For a primitive, the label IS the value. For an object, the label points to the mailbox (heap address), not the contents.

The String Pool (String Interning)

Engines may intern or deduplicate some strings as an implementation optimization, but this behavior and its memory savings are not a JavaScript language guarantee. Equal primitive strings compare by value, regardless of whether an engine shares internal storage.

📝 String Literals

Two occurrences of the primitive string "hello" have the same string value. V8 may share an internal representation, but programs must not depend on that implementation detail or assume a particular memory slot.

🏭 new String()

new String("hello") creates a String wrapper object, so it is not strictly equal to the primitive string "hello". Avoid using the wrapper in application code; claims about where it is stored or how the engine optimizes its representation are implementation details.

Garbage Collection

JavaScript has automatic memory management. When an object is no longer reachable from any variable, the Garbage Collector (GC) will eventually find it and free its memory. You don't need to do this manually (unlike C/C++).

🌳 Reachability — The Core Concept

An object is reachable when the runtime can reach it through references from roots such as active execution state, globals or host-held references. The exact roots and implementation details vary by engine and host.


An object is unreachable when no live reference path reaches it. It then becomes eligible for garbage collection, but collection is nondeterministic; assigning one variable to null is not sufficient if another reference still exists.

let user = { name: "Alice" }; // Object is reachable via user user = null; // this binding no longer refers to the object // If no other references remain, it becomes eligible for GC (timing is not guaranteed)

🕳️ Memory Leaks

A memory leak happens when objects remain reachable but you no longer need them. The GC won't collect them because they're still "reachable." Common causes:

1. Global Variables ›

Data attached to a long-lived global can stay reachable for the lifetime of that reference. In classic non-strict scripts, an undeclared assignment can create a global property; strict mode and JavaScript modules throw instead. Remove or replace unintended long-lived references when they are no longer needed.

function leaky() { bigData = new Array(1000000); // classic sloppy script: may create a global; strict/module code throws }
2. Forgotten Event Listeners ›

A listener can retain its callback and anything the callback closes over while the listener/target remains reachable. Removing an element from the DOM does not automatically prove a leak: if no live references keep the detached subtree reachable, the cycle can be collected. Clean up subscriptions/listeners when the owning component or long-lived target is done with them.

const btn = document.getElementById('btn'); btn.addEventListener('click', handler); // Removing btn from DOM alone does not prove a leak; check retaining paths // Remove listeners when needed: btn.removeEventListener('click', handler)
3. Closures Holding References ›

Closures can retain outer bindings while the closure remains reachable. If a long-lived callback actually references a large object, that object may remain reachable and increase memory use until the retaining path is removed.

const bigObj = { data: new Array(1e6) }; setInterval(() => { console.log(bigObj.data.length); // keeps bigObj alive! }, 1000);
4. Detached DOM Nodes ›

If you remove a DOM element but keep a JS reference to it, that element and its children remain in memory even though they're not visible.

🕵️ Hidden Classes — How V8 Optimizes Objects

V8 commonly uses internal object-shape metadata (often discussed as hidden classes or maps) to optimize property access. Similar property layouts may share shape information, but the exact rules are engine-version implementation details, and optimization does not mean every access becomes a guaranteed fixed-offset lookup.

✅ Consistent Shape

function Point(x, y) { this.x = x; this.y = y; } // All Points share hidden class C2 // Fast property access!

⚠️ Shape Changes Can Affect Optimization

const obj = {}; obj.x = 1; // class C1 obj.y = 2; // class C2 // Adding properties can change shape metadata in some engines // Measure hot paths before optimizing object construction

⚡ Inline Caching (IC)

Inline caches can specialize frequent operations based on observed receiver shapes and may speed up hot property access. A polymorphic or megamorphic call site can use different strategies; it does not mean that V8 simply gives up all optimization or always falls back to a fixed “slow lookup.”


Stable object construction can help some hot paths, but performance effects depend on engine version, workload and surrounding code. Profile before making shape consistency a rule or refactoring for it.

🗺️
Analogy: First time you drive to work, you look at the map. Second time, you remember the route. If you always go to the same place the same way, you never need the map again. Inline caching is V8's "memorized route."

🚧 Memory Limits

Stack Size

Limits depend on the engine, host, platform and call shape. Deep recursion can overflow the call stack, but there is no portable megabyte or frame-count threshold. Avoid unbounded recursion when input depth can grow; use an iterative algorithm when that fits the problem.

Heap Size

Heap limits depend on V8 version, process architecture, host policy, available resources and launch settings. Node.js exposes options such as --max-old-space-size, but increasing a limit consumes more memory and does not fix an unbounded allocation or leak. Browser limits differ and are not a portable per-tab constant.

Out of Memory

Excessive memory use may lead to allocation failures, tab/process termination or host-specific error messages. Exact wording and recovery behavior vary by runtime; investigate retained objects, allocation growth and configured limits before increasing capacity.

Generations

V8 has used generational collection strategies to treat short-lived and long-lived objects differently; details can change by version and memory space. This is a V8 implementation detail, not a rule that every JavaScript host uses the same generations or collection schedule.

Closures & Memory

A closure lets a function access lexical bindings from its defining environment after the outer call has returned. Values actually retained by a reachable closure can stay live; the runtime may optimize environments and does not have to retain unrelated local values.

🧲 How Closures Keep Memory Alive

Conceptually, a closure retains access to the outer bindings it needs. The engine’s environment representation is implementation-dependent; a captured value can remain reachable while the closure is reachable, but do not assume every local variable becomes a distinct heap object.

💡 Closures are Useful

Closures enable: private state, factory functions, callbacks with context, module patterns. They're one of JS's most powerful features — just be mindful of what they hold in memory.

function makeCounter() { let count = 0; // retained by the returned closure when needed return function() { count++; // still accesses count from outer scope return count; }; } const counter = makeCounter(); // makeCounter() returned, but count is STILL alive in heap // because counter closure holds a reference to it counter(); // 1 counter(); // 2 // when no reachable reference retains the closure, its data becomes eligible for GC

References & Memory Addresses

JavaScript exposes object identity and references through its language semantics, not through portable numeric memory addresses. Engines may move objects during garbage collection or use optimized representations, so a diagram label such as 0x7f3a12b0 is illustrative rather than an address a JavaScript program can inspect.

🔢 What is a Memory Address?

At a lower level, memory is addressed by runtimes and hardware, but ordinary JavaScript code cannot read or depend on an object’s address. Think of a reference as an abstract way to reach an object, not as a numeric pointer stored in a variable.

🆔 Unique Identity

Two separate object literals create different object identities, so {} === {} is false. JavaScript compares object identity here; the language does not require comparing or exposing physical memory addresses.

const a = { x: 1 }; // one object identity const b = { x: 1 }; // a distinct object identity console.log(a === b); // false — distinct objects const c = a; // c refers to the same object as a console.log(a === c); // true — same object identity
