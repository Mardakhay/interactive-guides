01
React Router v7
Client-side navigation for Single Page Applications

SPA vs Traditional (MPA) Websites

Before we look at code, it's essential to understand why React Router exists. Traditional websites reload the entire page on every click. React apps don't — and React Router is what makes that possible.

Navigation Model Comparison

❌ Traditional (MPA)

  • Browser requests new HTML from server on every click
  • Full page reload — screen flashes blank
  • Each navigation = new HTTP round-trip
  • Slow, jarring transitions

✅ SPA with React Router

  • One HTML file is loaded initially
  • Navigation happens entirely in the browser
  • Only the relevant component re-renders
  • URL changes but page never fully reloads

React Router v7 made a key change: the package is now react-router instead of react-router-dom. Everything else imports from there.

Setting Up Routes

In v7, routes are defined as an array of objects rather than JSX <Route> elements. This is cleaner, more testable, and easier to reason about.

router.tsx 
import { createBrowserRouter } from 'react-router';
import Layout   from './components/Layout';
import Home     from './pages/Home';
import About    from './pages/About';
import Posts    from './pages/Posts';
import NotFound from './pages/NotFound';

export const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,         // Shared layout (nav + footer)
    children: [
      { index: true,  element: <Home />      }, // /
      { path: 'about',  element: <About />     }, // /about
      { path: 'posts',  element: <Posts />     }, // /posts
      { path: 'posts/:id', element: <PostDetail /> }, // /posts/42
      { path: '*',       element: <NotFound />  }, // 404
    ],
  },
]);
main.tsx 
import { createRoot }    from 'react-dom/client';
import { RouterProvider } from 'react-router';
import { router }        from './router';

createRoot(document.getElementById('root')!).render(
  <RouterProvider router={router} />

Link vs NavLink vs <a>

⚠️ Common Mistake

Never use a raw <a href="/about"> in React Router. It triggers a full page reload, discarding all your React state. Always use <Link to="/about">.

Navbar.tsx 
import { Link, NavLink } from 'react-router';

// Link — basic client-side navigation
<Link to="/about">About</Link>

// NavLink — auto-applies CSS class when route is active
<NavLink
  to="/"
  className={({ isActive }) => isActive ? 'nav-active' : ''}
>
  Home
</NavLink>

// Programmatic navigation (e.g., after login)
const navigate = useNavigate();
navigate('/dashboard'); // go forward
navigate(-1);            // go back (like browser back button)

Dynamic Routes with useParams

Adding :id to a path makes it dynamic — that segment captures whatever is in the URL and makes it available via useParams().

PostDetail.tsx 
import { useParams } from 'react-router';

function PostDetail() {
  // :id from URL → e.g. /posts/42 → id = "42"
  const { id } = useParams<{ id: string }>();

  const [post, setPost] = useState(null);

  useEffect(() => {
    fetch(`https://jsonplaceholder.typicode.com/posts/${id}`)
      .then(r => r.json())
      .then(setPost);
  }, [id]); // Re-fetch when id changes

  if (!post) return <p>Loading...</p>;
  return <h1>{post.title}</h1>;
}
🧠 Quiz — React Router
What is the purpose of the <Outlet /> component in React Router?
A It creates a new browser tab for each route
B It marks where child route components should be rendered inside a layout
C It replaces the entire page when navigating
D It handles authentication redirects

✅ Correct! <Outlet /> is a placeholder inside a layout component. When a child route matches, React Router renders it in place of <Outlet /> — keeping the navbar/footer intact.

❌ Not quite. <Outlet /> is where child route components get injected inside a parent layout. The navbar and footer stay — only the Outlet area changes.

Controlled Inputs — The Foundation

In React, form inputs are "controlled" — meaning the input's value is driven by React state, not by the DOM. This gives you complete control over what the user types.

LoginForm.tsx 
function LoginForm() {
  const [email,    setEmail]    = useState('');
  const [password, setPassword] = useState('');

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault(); // ← prevents page reload!
    console.log({ email, password });
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}                       // state → input
        onChange={e => setEmail(e.target.value)} // input → state
        placeholder="Email"
      />
      <input
        type="password"
        value={password}
        onChange={e => setPassword(e.target.value)}
        placeholder="Password"
      />
      <button type="submit">Login</button>
    </form>
  );
}

Object State — One State for Many Fields

When you have multiple fields, managing a separate state variable for each becomes tedious. Instead, use one useState with an object and a single universal handleChange function.

💡 The Key Trick

Use [e.target.name] (a computed property) as the key. This lets one handler update any field — the input's name attribute must match the state key exactly.

ContactForm.tsx 
interface FormData {
  name: string;
  email: string;
  message: string;
}

function ContactForm() {
  const [form, setForm] = useState<FormData>({
    name: '', email: '', message: ''
  });

  // One handler for ALL inputs
  const handleChange = (
    e: React.ChangeEvent<HTMLInputElement | HTMLTextAreaElement>
  ) => {
    const { name, value } = e.target;
    setForm(prev => ({ ...prev, [name]: value }));
    //               ↑ spread keeps other fields intact
  };

  return (
    <form>
      <input name="name"    value={form.name}    onChange={handleChange} />
      <input name="email"   value={form.email}   onChange={handleChange} />
      <textarea name="message" value={form.message} onChange={handleChange} />
    </form>
  );
}

Manual Validation

Validation means checking if the user's input is acceptable before submitting. The pattern is: run a validate() function, populate an errors object, and conditionally display error messages.

Validation logic 
const [errors, setErrors] = useState<Partial<Record<keyof FormData, string>>>({});

const validate = (): boolean => {
  const newErrors: typeof errors = {};

  if (!form.name.trim())
    newErrors.name = 'Name is required';

  if (!form.email.includes('@'))
    newErrors.email = 'Enter a valid email address';

  if (form.message.length < 10)
    newErrors.message = 'Message must be at least 10 characters';

  setErrors(newErrors);
  return Object.keys(newErrors).length === 0; // true = no errors
};

const handleSubmit = (e: React.FormEvent) => {
  e.preventDefault();
  if (validate()) {
    console.log('Submitted:', form);
  }
};

// In JSX — show error below each field:
{errors.email && <span className="error">{errors.email}</span>}
🧠 Quiz — Forms
In a controlled input, what does value={email} do?
A It sets an initial default value only, which the user can overwrite freely
B It makes React state the single source of truth — the input always reflects the state
C It validates the email format automatically
D It prevents the user from typing in the field

✅ Correct! With value={state}, the input's displayed value is always controlled by React state. The user can't change the input without an onChange handler updating that state.

❌ Not quite. value={state} makes React state the single source of truth. The input reads from state on every render, and onChange writes back to state when the user types.

03
React Hook Form
Declarative validation with fewer re-renders

Why a Library?

Manual Approach — Problems
  • ❌ Lots of repetitive boilerplate code
  • ❌ Every keystroke triggers a re-render
  • ❌ Validation logic scattered throughout
  • ❌ TypeScript types are cumbersome to set up
React Hook Form — Benefits
  • ✅ Minimal boilerplate with register()
  • ✅ Uncontrolled by default → fewer re-renders
  • ✅ Declarative validation rules inline
  • ✅ Excellent TypeScript generics support

Core API

register(name, rules)
Connects an input to RHF and applies validation rules
handleSubmit(fn)
Wraps your submit handler — only calls it if validation passes
formState.errors
Object containing error messages, keyed by field name
watch(name)
Subscribe to a field's live value (e.g., for password confirm)
reset()
Resets all fields and errors to default values

Complete Example

RegisterPage.tsx 
import { useForm } from 'react-hook-form';

interface RegisterForm {
  name: string;
  email: string;
  password: string;
}

function RegisterPage() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<RegisterForm>();

  const onSubmit = (data: RegisterForm) => {
    console.log('Success:', data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>

      <input {...register('name', {
        required: 'Name is required',
        minLength: { value: 2, message: 'Min 2 characters' }
      })} />
      {errors.name && <span>{errors.name.message}</span>}

      <input {...register('email', {
        required: 'Email is required',
        pattern: {
          value: /^[^\s@]+@[^\s@]+\.[^\s@]+$/,
          message: 'Enter a valid email'
        }
      })} />
      {errors.email && <span>{errors.email.message}</span>}

      <input type="password" {...register('password', {
        required: 'Password is required',
        minLength: { value: 6, message: 'Min 6 characters' }
      })} />
      {errors.password && <span>{errors.password.message}</span>}

      <button type="submit">Register</button>
    </form>
  );
}

Validation Rules Cheat Sheet

requiredField cannot be emptyrequired: 'Name is required'

maxLengthMaximum character countmaxLength: { value: 50, message: 'Too long' }

🧠 Quiz — React Hook Form
What does {...register('email', { required: 'Email required' })} actually do to the input?
A It adds a CSS error class to the input element
B It makes the input read-only
C It spreads ref, name, onChange, and onBlur props onto the input to connect it to RHF's tracking

✅ Correct! register() returns an object with ref, name, onChange, and onBlur. Spreading it onto the input connects that element to RHF's internal tracking system without needing any useState.

Context API
Share state across the component tree without prop drilling

The Prop Drilling Problem

Imagine you need the logged-in user's name in a deeply nested component. Passing it through every intermediate component — even ones that don't use it — is called prop drilling.

Prop Drilling vs Context

❌ Prop Drilling

<App user={user}> ← has it
<Layout user={user}> ← passes it
<Sidebar user={user}> ← passes it
<UserMenu user={user}> ← uses it

✅ Context

<UserContext.Provider>
<App>
<Sidebar> ← doesn't care
<UserMenu> ← reads directly

3 Steps to Use Context

1

Create the Context (createContext)

Define the shape of the data your context will hold. This is typically done in its own file.

2

Provide the Value (Provider)

Wrap the part of your component tree that needs access with <Context.Provider value={...}>. Everything inside can access the value.

3

Consume the Value (useContext)

Any component inside the Provider can call useContext(MyContext) to get the value directly — no props needed.

context/ThemeContext.tsx 
import { createContext } from 'react';

interface ThemeContextType {
  isDark: boolean;
  toggle: () => void;
}

export const ThemeContext = createContext<ThemeContextType>({
  isDark: false,
  toggle: () => {},  // default no-op
});
App.tsx 
function App() {
  const [isDark, setIsDark] = useState(false);
  const toggle = () => setIsDark(prev => !prev);

  return (
    <ThemeContext.Provider value={{ isDark, toggle }}>
      <Layout />  {/* Everything inside can access ThemeContext */}
    </ThemeContext.Provider>
  );
}
ThemeToggle.tsx 
import { useContext } from 'react';
import { ThemeContext } from './context/ThemeContext';

function ThemeToggle() {
  // No props needed — reads directly from Context
  const { isDark, toggle } = useContext(ThemeContext);

  return (
    <button onClick={toggle}>
      {isDark ? '☀️ Light Mode' : '🌙 Dark Mode'}
    </button>
  );
}

Custom Provider + Custom Hook Pattern

In real projects, you'll almost always wrap the Provider in a dedicated component and expose a custom hook. This hides implementation details and gives you a clean API.

context/AuthContext.tsx 
const AuthContext = createContext<AuthContextType>({} as AuthContextType);

// Custom Provider — encapsulates all auth logic
export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const login  = (email: string) => setUser({ id: 1, email });
  const logout = () => setUser(null);

  return (
    <AuthContext.Provider value={{ user, login, logout, isLoggedIn: user !== null }}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom Hook — clean API for consumers
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;
}

// Usage anywhere in the tree:
function Profile() {
  const { user, logout } = useAuth(); // clean and simple!
}
⚠️ Performance Warning

Every time the context value changes, all consumers re-render. Context is ideal for infrequently changing data (user auth, theme, language). For frequently changing data (like a counter that updates every second), consider a more targeted solution or split contexts.

When to Use Context

Good Use CasesPoor Use Cases
✓ Authentication state (user login)✗ Rapidly changing data (animations)
✓ Theme (dark/light mode)✗ Server data (use React Query instead)
✓ Language/locale settings✗ Complex state with many actions
✓ Shopping cart items~ Very large apps (consider Zustand/Redux)
🧠 Quiz — Context API
You have AuthProvider wrapping your app. A <Sidebar> component doesn't need auth but has a child <UserMenu> that does. What's the correct approach?
A Pass the user as a prop through Sidebar down to UserMenu
B Call useAuth() directly inside UserMenu — Sidebar doesn't need to do anything
C Create a separate copy of AuthContext inside Sidebar
D Add another AuthProvider just for Sidebar

✅ Exactly right! This is the whole point of Context — UserMenu calls useAuth() and gets the user directly from the nearest Provider above it in the tree. Sidebar doesn't need to know about it at all.

❌ Not quite. With Context, UserMenu can call useAuth() directly without Sidebar doing anything. That's the whole point — it reads from the Provider ancestor, skipping all the intermediary components.

useReducer
Manage complex state with predictable action-based updates

What is useReducer?

useReducer is an alternative to useState when your state logic involves multiple sub-values or when the next state depends on the previous one. It's inspired by Redux and uses an Action → Reducer → New State pattern.

useReducer Data Flow
Component
calls dispatch({ type: 'ADD', text: '...' })
↓
Reducer Function
(state, action) → newState
switch(action.type) → returns new state
↓
New State
triggers re-render
↓
Component re-renders

Todo List with useReducer

todoReducer.ts 
// Define all possible action shapes with a discriminated union
type Action =
  | { type: 'ADD';    text: string }
  | { type: 'TOGGLE'; id: number }
  | { type: 'DELETE'; id: number };

function todoReducer(state: Todo[], action: Action): Todo[] {
  switch (action.type) {

    case 'ADD':
      return [
        ...state,
        { id: Date.now(), text: action.text, completed: false }
      ];

    case 'TOGGLE':
      return state.map(t =>
        t.id === action.id ? { ...t, completed: !t.completed } : t
      );

    case 'DELETE':
      return state.filter(t => t.id !== action.id);

    default:
      return state;
  }
}

// Usage in a component:
const [todos, dispatch] = useReducer(todoReducer, []);

dispatch({ type: 'ADD',    text: 'Learn useReducer' });
dispatch({ type: 'TOGGLE', id: 123 });
dispatch({ type: 'DELETE', id: 123 });

Context + useReducer = Global State

This is the most powerful pattern in this module. Combine Context (to make state globally accessible) with useReducer (to handle complex state changes). This is essentially a mini-Redux.

context/TodoContext.tsx 
const TodoContext = createContext<{
  todos: Todo[];
  dispatch: React.Dispatch<Action>;
}>({} as any);

export function TodoProvider({ children }: { children: React.ReactNode }) {
  const [todos, dispatch] = useReducer(todoReducer, []);

  return (
    <TodoContext.Provider value={{ todos, dispatch }}>
      {children}
    </TodoContext.Provider>
  );
}

export const useTodos = () => useContext(TodoContext);

// AddTodo.tsx — writes to global state
function AddTodo() {
  const { dispatch } = useTodos();
  dispatch({ type: 'ADD', text: 'New task' });
}

// TodoList.tsx — reads from global state
function TodoList() {
  const { todos } = useTodos();
  return <ul>{todos.map(t => <li key={t.id}>{t.text}</li>)}</ul>;
}

Always start with the simplest tool (useState). Only reach for more complex solutions when you actually have the problem they solve. Don't over-engineer from the start.

✅ Solution
counterReducer.ts — COMPLETE
function counterReducer(state: number, action: Action): number {
  switch (action.type) {
    case 'INC':   return state + 1;
    case 'DEC':   return state - 1;
    case 'RESET': return 0; // ← simply return 0
    default:       return state;
  }
}

The key insight: a reducer always returns the new state value. For RESET, that's simply 0. The reducer doesn't mutate anything — it just returns a new value.

🧠 Quiz — useReducer
In a reducer function, why should you never directly mutate the state object (e.g., state.count++)?
A JavaScript doesn't allow mutation of function parameters
B React uses reference equality to detect state changes — mutating won't trigger a re-render
C TypeScript will throw a compile error
D It's just a style convention with no functional impact

✅ Correct! React compares the old and new state with ===. If you mutate the object directly, the reference stays the same, React thinks nothing changed, and no re-render happens. Always return a new state object.

❌ Not quite. React detects state changes by comparing object references (===). Mutating the existing object keeps the same reference, so React sees "old state === new state" and skips the re-render. Always return a new object/array.

📚 BookClub — A Reading Tracker App

You'll build a small SPA that lets users browse books, add new ones via a form, and track reading status. It uses all three pillars from this module.

  • Multiple pages with React Router v7 (Home, Books, Add Book)
  • A form with validation (React Hook Form) to add new books

  • Dynamic route /books/:id for book detail page

Step-by-Step Guide

1

Project Setup

Create a new Vite + React + TypeScript project and install dependencies.

2

Create the Book Context + Reducer

Define the Book type, action types (ADD_BOOK, TOGGLE_READ, DELETE_BOOK), and set up the BookContext with useReducer.

3

Create router.tsx with routes: /, /books, /books/:id, /add, and a 404 catch-all. Wrap everything in a Layout component.

Starter Code

context/BookContext.tsx
import { createContext, useContext, useReducer } from 'react';

interface Book {
  id: number;
  title: string;
  author: string;
  year: number;
  isRead: boolean;
}

type Action =
  | { type: 'ADD_BOOK';    book: Omit<Book, 'id' | 'isRead'> }
  | { type: 'TOGGLE_READ'; id: number }
  | { type: 'DELETE_BOOK'; id: number };

function bookReducer(state: Book[], action: Action): Book[] {
  switch (action.type) {
    case 'ADD_BOOK':
      return [...state, { ...action.book, id: Date.now(), isRead: false }];
    case 'TOGGLE_READ':
      return state.map(b => b.id === action.id ? { ...b, isRead: !b.isRead } : b);
    case 'DELETE_BOOK':
      return state.filter(b => b.id !== action.id);
    default: return state;
  }
}

const BookContext = createContext<{
  books: Book[];
  dispatch: React.Dispatch<Action>;
}>({} as any);

export function BookProvider({ children }: { children: React.ReactNode }) {
  const [books, dispatch] = useReducer(bookReducer, [
    { id: 1, title: 'Clean Code', author: 'Robert Martin', year: 2008, isRead: true },
    { id: 2, title: 'The Pragmatic Programmer', author: 'Hunt & Thomas', year: 1999, isRead: false },
  ]);
  return (
    <BookContext.Provider value={{ books, dispatch }}>
      {children}
    </BookContext.Provider>
  );
}

export const useBooks = () => useContext(BookContext);

import { useNavigate } from 'react-router';
import { useBooks }  from '../context/BookContext';

interface FormValues { title: string; author: string; year: number; }

function AddBook() {
  const { dispatch } = useBooks();
  const navigate    = useNavigate();
  const { register, handleSubmit, formState: { errors } } = useForm<FormValues>();

  const onSubmit = (data: FormValues) => {
    dispatch({ type: 'ADD_BOOK', book: data });
    navigate('/books'); // redirect after adding
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input placeholder="Book Title"
        {...register('title', { required: 'Title is required', minLength: { value: 2, message: 'Min 2 chars' } })} />
      {errors.title && <span>{errors.title.message}</span>}

      <input placeholder="Author"
        {...register('author', { required: 'Author is required' })} />
      {errors.author && <span>{errors.author.message}</span>}

      <input type="number" placeholder="Year"
        {...register('year', {
          required: 'Year is required',
          min: { value: 1900, message: 'Year must be after 1900' },
          max: { value: 2030, message: 'Invalid year' }
        })} />
      {errors.year && <span>{errors.year.message}</span>}

      <button type="submit">Add Book</button>
    </form>
  );
}
