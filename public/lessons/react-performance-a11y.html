01
The Problem

The Re-render Cascade

React's default behavior is to re-render a component AND all of its children whenever state changes — even if a child's props haven't changed. This cascading re-render is the root cause of most React performance issues.

🔵 <Button> +count

🔵 <DeepChild> static

🔵 <Button> +count

02
Memoization

React.memo HOC

React.memo is a Higher-Order Component that wraps your component and caches the rendered output. It performs a shallow comparison of props — if they haven't changed, React skips re-rendering entirely and reuses the last result.

❌ Without memo
function ExpensiveChild({ name }) { console.log('🔴 Renders every time!'); // Expensive computation... return <div>Hello, {name}</div>; } // Parent re-renders → child re-renders // even when name="Nurlan" never changes!
✅ With React.memo
const ExpensiveChild = React.memo( function ExpensiveChild({ name }) { console.log('🟢 Only when props change!'); return <div>Hello, {name}</div>; } ); // Parent re-renders → memo checks props // name unchanged → SKIP! ✅
REACT.MEMO DECISION FLOW
🔄 Parent re-renders
⚖️ prevProps === nextProps?
(shallow comparison)
✅ Equal Reuse cached output
❌ Not equal Re-render component

When to use React.memo

SituationUse memo?Reason
Component renders frequently, props rarely change✅ YesAvoids expensive re-renders
Component does heavy computation✅ YesComputation cost outweighs memo overhead
Simple/cheap component (e.g. <p> wrapper)❌ NoMemo overhead > render cost
Props change on every parent render❌ NoComparison runs but always fails — wasteful
Receives objects/arrays as props without useCallback/useMemo⚠️ CarefulNew reference each render breaks shallow comparison
Custom areEqual — fine-grained control
const UserCard = React.memo( function UserCard({ user, theme }) { return ( <div style={{ color: theme.text }}> <h3>{user.name}</h3> <p>{user.email}</p> </div> ); }, // Custom comparison — true = SKIP render, false = RE-RENDER (prevProps, nextProps) => { return ( prevProps.user.id === nextProps.user.id && prevProps.user.name === nextProps.user.name && prevProps.theme.text === nextProps.theme.text ); } );
03
Hook

useMemo Hook

useMemo caches the result of an expensive calculation. It only re-runs the function when its dependencies change. Think of it as a smart cache for derived values — filter results, sorted arrays, computed styles.

❌ Recalculates every render
function ProductList({ products, search }) { // ❌ Runs on EVERY render — even when // only an unrelated state changes! const filtered = products.filter(p => p.name.toLowerCase().includes( search.toLowerCase() ) ); return <ul>{filtered.map(p => ( <li key={p.id}>{p.name}</li> ))}</ul>; }
✅ Cached with useMemo
import { useMemo } from 'react'; function ProductList({ products, search }) { // ✅ Only re-runs when products or // search actually changes const filtered = useMemo(() => { return products.filter(p => p.name.toLowerCase().includes( search.toLowerCase() ) ); }, [products, search]); // ← deps array return <ul>...filtered results...</ul>; }
useMemo EXECUTION FLOW
🔄 Component renders
🔍 Have dependencies [deps] changed?
✅ No change Return cached value
❌ Changed! Run fn(), cache result

Best use cases for useMemo

📊 Large List Filtering

Filtering/sorting arrays of 100+ items. Without memo, this runs on every keystroke, scroll, or unrelated state update.

🧮 Heavy Calculations

Statistical computations, data transformations, chart data processing — anything measurably expensive via profiling.

🎨 Style Objects

When passing style objects to a React.memo child — without useMemo, a new object reference breaks memo's comparison.

04
Hook

useCallback Hook

useCallback caches the function itself — its reference stays stable across renders. This matters because in JavaScript, () => {} creates a new function object on every call. Pass a new function to a memoized child, and memo's comparison fails, defeating the optimization.

💡
Key insight: In JavaScript, fn1 === fn2 is false even if they do exactly the same thing. Functions are objects — every () => {} creates a fresh object reference. useCallback prevents this.
❌ memo is broken
function Parent() { const [count, setCount] = useState(0); // ❌ NEW function object every render! const handleClick = () => { console.log('Clicked!'); }; return ( <div> <button onClick={() => setCount(c => c+1)}> {count} </button> {/* memo FAILS — handleClick is always new */} <MemoizedChild onClick={handleClick} /> </div> ); }
✅ Stable reference with useCallback
import { useCallback } from 'react'; function Parent() { const [count, setCount] = useState(0); // ✅ Same function reference across renders const handleClick = useCallback(() => { console.log('Clicked!'); }, []); // no deps → never recreated return ( <div> <button onClick={() => setCount(c => c+1)}> {count} </button> {/* memo WORKS — stable reference ✅ */} <MemoizedChild onClick={handleClick} /> </div> ); }
useMemo vs useCallback — THE RELATIONSHIP
// useCallback is actually just syntactic sugar over useMemo: const memoFn = useCallback(fn, deps); // is exactly equivalent to: const memoFn = useMemo(() => fn, deps); // useMemo → caches the RETURN VALUE of the function // useCallback → caches the FUNCTION ITSELF
⚠️
The Golden Rule: Only use useCallback when passing a function to a child wrapped with React.memo. Using it elsewhere adds overhead without benefit. Don't wrap every function "just in case."

🌍 Real-world: E-Commerce Product Page

ProductPage.jsx — All three working together
import { useState, useMemo, useCallback } from 'react'; function ProductPage() { const [search, setSearch] = useState(''); const [cart, setCart] = useState([]); const [products] = useState(() => generateProducts(10000)); // ✅ useMemo: 10,000 products filtered only when search changes const filtered = useMemo(() => products.filter(p => p.name.toLowerCase().includes(search.toLowerCase()) ) , [products, search]); // ✅ useCallback: stable reference for memo'd child const addToCart = useCallback((product) => { setCart(prev => [...prev, product]); }, []); // no deps — setCart is stable return ( <div> <SearchBar onSearch={setSearch} /> <CartBadge count={cart.length} /> <ProductList products={filtered} onAdd={addToCart} /> </div> ); } // ✅ React.memo: re-renders only when products/onAdd change const ProductList = React.memo( function ProductList({ products, onAdd }) { return ( <ul> {products.map(p => ( <ProductCard key={p.id} product={p} onAdd={onAdd} /> ))} </ul> ); } ); // Result: cart changes don't re-render ProductList 🎯

Lazy Loading

By default, your entire React app ships as one big JavaScript bundle. Every route, every component — loaded upfront, even for pages the user may never visit. React.lazy() + dynamic import() splits your bundle into chunks that load on-demand.

❌ Eager loading (2.5MB upfront)
// ❌ ALL routes loaded immediately import Dashboard from './pages/Dashboard'; import Settings from './pages/Settings'; import AdminPanel from './pages/AdminPanel'; import Reports from './pages/Reports'; // User visits "/" — but pays for ALL 2.5MB // Even if they never visit /admin!
✅ Lazy loading (200kb → on-demand)
import { lazy, Suspense } from 'react'; // ✅ Each becomes its own JS chunk const Dashboard = lazy( () => import('./pages/Dashboard') ); const AdminPanel = lazy( () => import('./pages/AdminPanel') ); function App() { return ( <Suspense fallback={<Loading />}> <Routes> <Route path="/dashboard" element={<Dashboard />} /> <Route path="/admin" element={<AdminPanel />} /> </Routes> </Suspense> ); }
💡
Key requirement: Lazy-loaded components must use export default. Named exports don't work with React.lazy(). Vite/Webpack automatically create separate .chunk.js files for each dynamic import.

Bundle Size Matters

Every kilobyte of JavaScript must be downloaded, parsed, and executed before your app becomes interactive. Large bundles = slow TTI (Time to Interactive). Here are the strategies to keep bundles lean.

🌲 Tree Shaking

Modern bundlers (Vite, Webpack 5) remove unused exports. Use named imports: import {'{ format }'} from 'date-fns' instead of the whole library.

📊 Bundle Analysis

Use vite-bundle-visualizer or webpack-bundle-analyzer to see what's taking up space. Run it before and after optimizations.

🗜️ Compression

Enable gzip/Brotli on your server. Brotli gives ~20% better compression than gzip. Most CDNs handle this automatically.

⚠️
Premature Optimization Warning — Don't optimize blindly. Use Chrome DevTools Performance tab or React Profiler to measure first. Optimization has overhead — adding useMemo to a fast component makes it slower. The rule: Profile → Identify → Optimize → Measure again.

Accessibility · a11y

Build for Everyone

~15% of the world's population lives with some form of disability. Accessibility (a11y) ensures your app works for screen reader users, keyboard-only users, people with visual impairments, and more. It's also increasingly a legal requirement.

👁️ Visual

Screen readers, high contrast mode, zoom support. Use semantic HTML and ARIA labels to describe your UI.

🖐️ Motor

Keyboard-only navigation, switch access, voice control. Every interaction must be reachable without a mouse.

🧠 Cognitive

Clear structure, consistent layouts, plain language, no auto-playing media, sufficient contrast ratios (4.5:1 min).

⌨️ Keyboard Navigation

Essential keyboard shortcuts every user relies on:
Tab → Next focusable element
Shift + Tab → Previous element
Enter → Activate link / button
Space → Activate checkbox / button / toggle
Esc → Close modal / dropdown / dialog
↑↓ → Navigate menu items / listbox options

💡
First Rule of ARIA: "No ARIA is better than bad ARIA." Always prefer native HTML elements first — <button>, <a>, <input>. They include keyboard support and screen reader semantics for free.
