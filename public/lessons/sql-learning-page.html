Introduction & Origins
Why SQL exists, where it came from, why it's still dominant 50+ years later
Concept What is SQL?

SQL (Structured Query Language) is the standard language for communicating with relational databases — systems that organize data into structured tables of rows and columns. Unlike procedural languages where you specify how to do something step by step, SQL is declarative: you describe what data you want, and the database engine decides the most efficient retrieval strategy.


Think of a relational database as a set of interconnected spreadsheets. Each table has named columns with defined data types. SQL is the language you use to query, transform, and manage that data.

History The 1970s at IBM

The foundations were laid by Dr. Edgar F. Codd, a mathematician at IBM who published his landmark 1970 paper introducing the relational model based on set theory and relational algebra. His ideas were refined by Donald Chamberlin and Raymond Boyce, who developed SEQUEL (later SQL) at IBM — giving rise to IBM DB2 and Oracle. SQL was standardized by ANSI in 1986; the widely implemented standard is SQL-92.

📊
Despite being over 50 years old, relational databases power roughly 70% of production systems today. SQL remains one of the most sought-after technical skills in data, engineering, and business roles.
💡
Declarative vs Imperative: In Python you'd loop through rows. In SQL you write SELECT name FROM users WHERE age > 30 — and the optimizer decides whether to use an index, full scan, etc.

Relational Algebra
The mathematical foundation SQL is built upon — understanding this makes SQL intuitive
Concept Why Relational Algebra Matters

SQL is not arbitrary — it was built directly from relational algebra, a formal branch of mathematics that defines operations on sets of data called relations (tables). Every operation takes one or more relations as input and produces a new relation as output. This "table in, table out" consistency is what makes SQL queries composable — you can nest them arbitrarily deep.


Understanding these operations clarifies why SQL behaves the way it does: why UNION requires matching column counts, how JOIN works under the hood, and why every subquery must produce a valid table.

Example Relational Algebra → SQL

The expression σage>30(πname,age(employees)) — project name and age, then filter — becomes:

SQL
-- π (Projection) → SELECT clause: choose columns
-- σ (Selection)  → WHERE clause: filter rows
SELECT name, age          -- π: keep only these columns
FROM   employees
WHERE  age > 30;          -- σ: filter rows

The SELECT Statement
The most fundamental SQL command — retrieving, shaping, and transforming data
Syntax Basic Structure

SELECT requires at minimum two clauses: SELECT (which columns) and FROM (which table).

SQL
-- Explicit columns (preferred in production)
SELECT column1, column2
FROM   table_name;

-- Wildcard: retrieves ALL columns (fine for exploration)
SELECT * FROM employees;
⚠️
Avoid SELECT * in production. It retrieves unnecessary data, inflates network transfer, and can silently break queries if table columns are added, removed, or reordered.
Concept Expressions, Aliases & Computed Columns

The SELECT clause accepts arithmetic expressions, function calls, and string operations. Use AS to give computed columns readable names.

SQL
-- Arithmetic expression with alias
SELECT order_id,
       unit_price * quantity AS total
FROM   order_details;

-- String concatenation (PostgreSQL uses ||)
SELECT first_name || ' ' || last_name AS full_name
FROM   employees;

-- Extract a component from a date
SELECT last_name,
       hire_date,
       DATE_PART('year', hire_date) AS hire_year
FROM   employees;

-- Format a date as readable text
SELECT TO_CHAR(hire_date, 'Month YYYY') AS hire_month
FROM   employees;

Syntax LIKE Wildcards

% matches zero or more characters. _ matches exactly one character.

SQL
WHERE name LIKE 'M%'    -- starts with M
WHERE name LIKE '%son'  -- ends with "son"
WHERE name LIKE '%ill%' -- contains "ill"
WHERE name LIKE '_a%'   -- 2nd char is "a"
Syntax IN and BETWEEN
SQL
-- IN: clean shorthand for multiple ORs
WHERE supplier_id IN (2, 4, 6, 8)

-- BETWEEN: inclusive on both ends
WHERE unit_price BETWEEN 20 AND 30
-- same as:
WHERE unit_price >= 20
  AND unit_price <= 30
Concept NULL — The Absence of Value

NULL represents the absence of a value — not zero, not an empty string, but truly unknown or not applicable.


⚠️
Critical NULL rule: WHERE region = NULL will never match any row — not even rows where region IS NULL. NULL cannot be compared using = or !=. Always use IS NULL or IS NOT NULL.
SQL
-- ❌ WRONG: matches absolutely nothing, ever
SELECT * FROM employees WHERE region = NULL;

-- ✅ CORRECT
SELECT * FROM employees WHERE region IS NULL;
SELECT * FROM employees WHERE region IS NOT NULL;
💡
SUM(), AVG(), MIN(), MAX() all skip NULLs. COUNT(*) counts every row including NULLs. COUNT(column) counts only non-NULL values in that column.
Syntax Sorting, Limiting & DISTINCT
SQL
-- ORDER BY: ASC (default) or DESC
SELECT product_name, unit_price
FROM   products
ORDER BY unit_price DESC;

-- LIMIT: cap the rows returned
SELECT product_name, unit_price
FROM   products
ORDER BY unit_price DESC
LIMIT 5;

-- DISTINCT: remove duplicate rows
SELECT DISTINCT country FROM customers;

-- Count unique values
SELECT COUNT(DISTINCT country) FROM customers;

Aggregation, Grouping & Subqueries
Summarising data with GROUP BY, HAVING, and nesting queries inside queries
Concept Aggregate Functions
FunctionBehaviorNULL handling
COUNT(*)Count all rowsIncludes NULLs
COUNT(col)Count non-NULL valuesSkips NULLs
SUM(col)Sum numeric valuesSkips NULLs
AVG(col)Average numeric valuesSkips NULLs (may surprise!)
MIN(col)Smallest value (any type)Skips NULLs
MAX(col)Largest value (any type)Skips NULLs
⚠️
The mixing rule: When aggregates appear in SELECT, every non-aggregated column must also appear in GROUP BY. Mixing without GROUP BY is an error.
Syntax GROUP BY and HAVING
SQL
-- GROUP BY: partition rows, then aggregate each group
SELECT   country, COUNT(customer_id) AS customer_count
FROM     customers
GROUP BY country
ORDER BY customer_count DESC;

-- HAVING: filter AFTER grouping (WHERE filters BEFORE grouping)
SELECT   country, COUNT(customer_id) AS cnt
FROM     customers
GROUP BY country
HAVING   COUNT(customer_id) > 5;

-- Both WHERE and HAVING in the same query:
SELECT   category_id, SUM(unit_price) AS total
FROM     products
WHERE    discontinued = 0        -- pre-group filter (fast)
GROUP BY category_id
HAVING   SUM(unit_price) > 100; -- post-group filter
✅
Mental model: WHERE = "Pre-group filter" (eliminates rows before grouping). HAVING = "Post-group filter" (eliminates groups after aggregation). Always prefer WHERE for raw-row conditions — it's faster.
Concept Subqueries — Queries Inside Queries

A subquery is a complete SQL query nested inside another. The result of the inner query feeds the outer query. They appear in three main positions:

Subquery in WHERE
-- Single-value subquery (use =)
SELECT product_name, unit_price
FROM   products
WHERE  unit_price = (SELECT MAX(unit_price) FROM products);

-- Multi-value subquery (use IN)
SELECT customer_id, order_id
FROM   orders
WHERE  order_id IN (
    SELECT order_id
    FROM   order_details
    WHERE  quantity > 100
);
Subquery in FROM (derived table)
-- Must be given an alias; acts as a temporary table
SELECT order_id
FROM  (
    SELECT order_id, SUM(quantity) AS total_items
    FROM   order_details
    GROUP BY order_id
    HAVING SUM(quantity) < 100
) AS small_orders;
Correlated Subquery (re-runs per outer row)
-- Inner query references a column from the outer query.
-- Re-evaluated for EACH ROW of the outer query — can be slow!
SELECT o.employee_id, o.order_id, o.ship_city
FROM   orders o
WHERE  o.ship_city = (
    SELECT e.city
    FROM   employees e
    WHERE  e.employee_id = o.employee_id  -- ← references outer row
);

WHERE filters rows BEFORE grouping. HAVING filters groups AFTER aggregation. You CANNOT use aggregate functions like COUNT() inside a WHERE clause.

Joining Tables
INNER JOIN, OUTER JOINs, multi-table chains, and detecting orphaned records
Concept What is a JOIN?

A JOIN retrieves data from multiple tables by matching rows on a shared key — usually a foreign key. Rather than duplicating data in one giant table, relational databases split data into focused tables and join them at query time.

SQL
-- ✅ Explicit JOIN syntax (always preferred)
SELECT e.last_name, e.first_name,
       COUNT(o.order_id) AS order_total
FROM   employees e
JOIN   orders o ON e.employee_id = o.employee_id
GROUP BY e.last_name, e.first_name
ORDER BY order_total DESC;

-- ❌ Implicit syntax (old style — avoid for clarity)
SELECT e.last_name, COUNT(o.order_id)
FROM   employees e, orders o
WHERE  e.employee_id = o.employee_id
GROUP BY e.last_name;

INNER JOIN

Only rows with a match in both tables. Non-matching rows are silently discarded.

LEFT JOIN

All rows from the left table. Unmatched right-table columns become NULL.

RIGHT JOIN

All rows from the right table. Unmatched left-table columns become NULL.

FULL OUTER JOIN

All rows from both tables. Unmatched columns on either side become NULL.

Example Multi-Table Join (3 tables)

Rule: For N tables joined, you need at least N−1 join conditions. Missing one causes a Cartesian product.

SQL
SELECT   e.last_name,
         SUM(d.unit_price * d.quantity) AS total_sales
FROM     employees e
JOIN     orders o        ON e.employee_id = o.employee_id   -- join #1
JOIN     order_details d ON o.order_id    = d.order_id     -- join #2
GROUP BY e.last_name
ORDER BY total_sales DESC
LIMIT    5;
Example Outer Join for Data Integrity Checks

LEFT JOIN + WHERE … IS NULL is a powerful pattern for finding orphaned records.

SQL
-- Find orders referencing a non-existent customer
SELECT o.order_id, o.customer_id
FROM   orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE  c.customer_id IS NULL;
-- Rows that survive: orders with NO matching customer
-- These are data integrity violations

✏ Try It

DDL — Defining Database Structure
CREATE TABLE, data types, constraints, and ALTER TABLE
DDL vs DML

DDL (Data Definition Language) defines and manages the structure of objects.
Commands: CREATE, ALTER, DROP.

DML (Data Manipulation Language) manages the data within those structures.
Commands: INSERT, UPDATE, DELETE, TRUNCATE.

Principle Design with Integrity

Choosing the right data types and constraints at design time is far cheaper than fixing bad data after it's in production. Constraints like NOT NULL, UNIQUE, and FOREIGN KEY act as a safety net — they prevent invalid data from ever entering the database.

Syntax CREATE TABLE with Full Constraints
SQL
DROP TABLE IF EXISTS items; -- prevent error if already exists

CREATE TABLE items (
    item_id     INT          PRIMARY KEY,           -- NOT NULL + UNIQUE
    item_code   VARCHAR(5)  UNIQUE,                -- no duplicates
    item_name   VARCHAR(40) NOT NULL DEFAULT ' ', -- required field
    quantity    INT          NOT NULL DEFAULT 0,   -- defaults to 0
    price       DECIMAL(9,2) NOT NULL DEFAULT 0
                             CHECK (price < 1000),  -- custom rule
    supplier_id INT,
    FOREIGN KEY (supplier_id)
        REFERENCES suppliers(supplier_id)
        ON DELETE NO ACTION    -- block delete if children exist
        ON UPDATE CASCADE      -- propagate key changes to children
);

DML — Inserting, Updating & Deleting
INSERT, UPDATE, DELETE, TRUNCATE — and why WHERE is never optional
Syntax INSERT — Adding Rows
SQL
-- Named columns (recommended — order-independent)
INSERT INTO employees (employee_id, last_name, first_name, title)
VALUES (20, 'Doe', 'Jane', 'Data Scientist');

-- Multiple rows in one statement
INSERT INTO employees (employee_id, last_name, first_name)
VALUES
    (21, 'Smith', 'Tom'),
    (22, 'Jones', 'Alice');

-- Bulk insert from another table
INSERT INTO items (item_id, item_name, quantity, price)
SELECT product_id, product_name, units_in_stock, unit_price
FROM   products;
Syntax UPDATE — Modifying Rows
SQL
-- WHERE is essential — without it EVERY row is updated!
UPDATE employees
SET    first_name = 'Timmy',
       title      = 'Senior Analyst'
WHERE  employee_id = 20;

-- Update based on calculation
UPDATE products
SET    unit_price = unit_price * 1.10  -- 10% price increase
WHERE  category_id = 3;
⚠️
Never skip WHERE in production UPDATE/DELETE. An UPDATE without WHERE modifies every single row in the table — a change that can be catastrophic and difficult to reverse.
Syntax DELETE vs TRUNCATE
SQL
-- DELETE: targeted removal, filterable, logged row-by-row
DELETE FROM employees
WHERE  employee_id IN (20, 21);

-- TRUNCATE: removes ALL rows instantly
-- Much faster; cannot be filtered; may not roll back easily
TRUNCATE TABLE employees;

Views, CASE & Set Operations
Virtual tables, conditional logic, UNION / INTERSECT / EXCEPT, and auto-increment keys
Concept Views — Named Stored Queries

A view is a named, stored query that behaves like a virtual table. It stores no data — it re-executes its underlying query on every access, so data is always current.


🔒
Security: Exclude sensitive columns (salaries, PII) and restrict users to the view rather than the base table.
🎭
Abstraction: Package complex joins and aggregations once. Others query SELECT * FROM view_name without understanding the internals.
SQL
DROP VIEW IF EXISTS employee_sales_summary;

CREATE VIEW employee_sales_summary AS
SELECT
    e.employee_id,
    e.first_name || ' ' || e.last_name AS full_name,
    TO_CHAR(SUM(od.unit_price * od.quantity), '999,999.00') AS total_sales
FROM   employees e
JOIN   orders o          ON e.employee_id = o.employee_id
JOIN   order_details od  ON o.order_id    = od.order_id
GROUP BY e.employee_id, e.first_name, e.last_name
ORDER BY SUM(od.unit_price * od.quantity) DESC;

-- Query the view exactly like a table:
SELECT * FROM employee_sales_summary;
Concept The CASE Expression

SQL has no if-then-else. CASE provides equivalent conditional logic usable anywhere a value is expected: in SELECT, ORDER BY, GROUP BY, and WHERE.

SQL
SELECT
    product_name, unit_price,
    CASE
        WHEN unit_price < 20  THEN 'Economy'
        WHEN unit_price < 80  THEN 'Standard'
        ELSE                       'Premium'
    END AS price_tier
FROM products;

-- CASE in ORDER BY for custom sort sequence:
ORDER BY
    CASE status
        WHEN 'urgent' THEN 1
        WHEN 'normal' THEN 2
        ELSE              3
    END;
Syntax UNION and Set Operations

Stacks two result sets vertically. Both queries must return the same column count with compatible types.

SQL
-- UNION: removes duplicates (slightly slower)
-- UNION ALL: keeps all rows including duplicates (faster)
SELECT category_name, SUM(units_in_stock) AS total
FROM   products
GROUP BY category_name

UNION ALL

SELECT 'Grand Total', SUM(units_in_stock)
FROM   products

ORDER BY total ASC;  -- applies to the COMBINED result

-- Other set operations:
-- INTERSECT: rows present in BOTH queries
-- EXCEPT:    rows in first query but NOT in second
✅
ORDER BY always goes at the very end of the last query in a UNION and applies to the entire combined result, not individual sub-queries.
Concept Auto-Incrementing Keys (IDENTITY)

When no natural unique identifier exists, use a surrogate key — a system-generated integer that auto-assigns on every insert.

SQL
CREATE TABLE customers (
    customer_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name   VARCHAR(100) NOT NULL
);

-- Omit customer_id — the database fills it automatically
INSERT INTO customers (full_name)
VALUES ('Alice'), ('Bob');
-- Alice gets 1, Bob gets 2 automatically
💡
Deleting a row does not reuse its identity value. Gaps in the sequence are normal — never try to fill them in. Reset with ALTER TABLE … ALTER COLUMN … RESTART WITH 1 if needed.

SQL Clause Execution Order
Why aliases don't work in WHERE, why aggregates fail there, and other "why doesn't this work?" mysteries — explained
Concept Written Order ≠ Processing Order

SQL queries are written in a specific order (SELECT…FROM…WHERE…) but the engine processes clauses in a completely different logical sequence. Understanding this resolves the most common "but why?" SQL errors.

01
FROM / JOIN
Build the full dataset — join all tables together first
02
WHERE
Filter individual rows before any grouping
03
GROUP BY
Partition filtered rows into groups
04
HAVING
Filter groups — aggregate functions now available
05
SELECT
Calculate expressions and assign column aliases
06
DISTINCT
Remove duplicate rows from the result
07
ORDER BY
Sort final result — SELECT aliases are now available here
08
LIMIT
Trim to the requested row count
💡
This explains everything:
• WHERE total > 100 fails if total is a SELECT alias — aliases don't exist until step 5.
• WHERE COUNT(*) > 5 fails — aggregates aren't computed until steps 3–4.
• HAVING country = 'USA' works but is slower than WHERE country = 'USA' — WHERE eliminates rows earlier (step 2).
• ORDER BY total can use a SELECT alias — ORDER BY runs at step 7, after SELECT creates aliases at step 5.
Example Common Execution Order Mistakes — and Their Fixes
SQL
-- ❌ FAILS: 'total_sales' alias used in WHERE (step 2),
--    but aliases are created in SELECT (step 5)
SELECT employee_id, SUM(amount) AS total_sales
FROM   sales
WHERE  total_sales > 1000;   -- alias doesn't exist yet!

-- ✅ FIX 1: use HAVING (step 4, after GROUP BY)
SELECT employee_id, SUM(amount) AS total_sales
FROM   sales
GROUP BY employee_id
HAVING SUM(amount) > 1000;

-- ✅ FIX 2: wrap in a subquery (alias exists in outer query)
SELECT *
FROM  (SELECT employee_id, SUM(amount) AS total_sales
        FROM   sales
        GROUP BY employee_id) AS sub
WHERE  sub.total_sales > 1000;

When filtering on an aggregate value, use HAVING (runs at step 4, after GROUP BY). WHERE (step 2) only sees raw column values — aggregates and SELECT aliases don't exist there yet.
