Section 01

Sync vs Async

JavaScript is single-threaded — it has one call stack and can only do one thing at a time. Understanding what "blocking" means and how JavaScript sidesteps it is the entire foundation of async programming.

🔵 Synchronous — Blocking Code

In synchronous code, every line is a checkpoint. The engine reads line 1, executes it completely, then moves to line 2. Nothing can interrupt this sequence. If line 2 takes 5 seconds (a huge calculation, a file read), the entire program freezes for those 5 seconds. The user sees a locked-up browser, events don't fire, nothing repaints.

This is called blocking because the thread is occupied — blocked — and cannot handle anything else.

js 
console.log('1 — Started');
console.log('2 — Processing...');
console.log('3 — Done');

// Output is always guaranteed to be in this exact order:
// 1 — Started
// 2 — Processing...
// 3 — Done
//
// Predictable. Safe. But inflexible — any slow operation STOPS everything.

🟢 Asynchronous — Non-blocking Code

Asynchronous code lets JavaScript offload slow operations — timers, network requests, disk reads — to the browser's Web APIs. These run in the background (outside the JS thread). When they complete, a callback is queued and JavaScript picks it up later, when the main thread is free.

Crucially: JavaScript itself never truly runs in parallel. It's still single-threaded. The browser does the waiting on its behalf, and JavaScript comes back to handle the result.

js 
console.log('1 — Started');    // → Call Stack → runs immediately

setTimeout(callback, 2000);    // → Handed OFF to browser timer API
                                // → JS does NOT wait — moves on instantly

console.log('3 — Continues');   // → Runs immediately after line 1

// ... 2 seconds pass in the background ...

function callback() {
  console.log('2 — After 2 seconds'); // Runs LAST, when timer fires
}

// Actual output:
// 1 — Started       (line 1, synchronous)
// 3 — Continues     (line 3, synchronous — skip past setTimeout)
// 2 — After 2 sec   (callback, async — after 2000ms)
//
// Line 3 runs BEFORE line 2 even though it comes later in the code!
💡

Real-world analogy: Imagine ordering coffee (async) vs waiting at the counter staring at the machine until it's done (sync). With async, you place your order, sit down, do other things, and the barista calls you when it's ready. The café (browser) does the waiting. You (JS thread) stay productive.

Section 02

The Event Loop

The Event Loop is JavaScript's concurrency model — the engine that makes async code possible without multi-threading. Understanding this deeply will explain every strange output order you ever see.

The Five Components

JavaScript runtime has several distinct areas. Each plays a specific role:

📚
Call Stack
Where code actually executes. Functions are pushed when called, popped when they return. LIFO (last-in, first-out). Only one frame executes at a time.
🧠
Heap
Unstructured memory where objects and variables are stored. The stack holds references to objects living here.
🔄
Event Loop
Continuously checks: is the Call Stack empty? If yes, moves the next item from a queue into the stack. This is the entire loop.
📋
Web APIs
Browser-provided async services: setTimeout, fetch, DOM events, XMLHttpRequest. They run outside the JS thread.
⚡
Microtask Queue
High-priority queue. Promises and queueMicrotask() land here. The Event Loop drains this queue completely before touching the Callback Queue. Even a new microtask added during processing runs before any macrotask.
📬
Callback Queue
Also called the Macrotask Queue. setTimeout, setInterval, I/O callbacks wait here. Lower priority than microtasks.
⚠️

Priority rule: When the Call Stack empties, the Event Loop checks the Microtask Queue FIRST and drains it completely — every last microtask — before moving even one item from the Callback Queue. This is why Promise .then() callbacks always run before setTimeout callbacks, even if the timeout is 0ms.

Step-by-Step Execution Trace

Here is the exact sequence for a piece of code that mixes all three types of execution:

js 
console.log('A');

setTimeout(() => console.log('B'), 1000);

new Promise((resolve) => {
  resolve('C');           // executor runs SYNCHRONOUSLY
}).then((v) => console.log(v));  // .then callback → Microtask Queue

console.log('D');

// ── EXECUTION ORDER ─────────────────────────────────────────────
// Step 1: console.log('A') → Call Stack → executes → prints "A"
// Step 2: setTimeout callback → handed to Web API, timer starts
// Step 3: Promise executor runs synchronously → resolve('C') called
//         → .then callback queued in Microtask Queue
// Step 4: console.log('D') → Call Stack → executes → prints "D"
// Step 5: Call Stack is now EMPTY
//         → Event Loop checks Microtask Queue → finds 'C' callback
//         → moves to Call Stack → prints "C"
// Step 6: Microtask Queue is empty
//         → 1 second passes → setTimeout callback → Callback Queue
//         → Event Loop moves it to Call Stack → prints "B"
//
// Final output:  A → D → C → B
🔑

The key insight: The Promise executor function (the code inside new Promise(fn)) runs synchronously — immediately, inline. Only the .then() callback is deferred to the Microtask Queue. This is why resolve() is called at step 3 but we only see "C" at step 5.

Section 03

Callbacks

Before Promises existed, callbacks were the way to handle async operations. They're simple and still used everywhere — but they have a critical flaw at scale.

What is a Callback?

A callback is simply a function passed as an argument to another function, to be called later. There's nothing magic about it — it's just a function reference. The receiving function decides when to call it.

The async pattern works because JavaScript functions are first-class values — you can pass them around like any other variable, store them, and invoke them later.

js 
// A function that accepts a callback
function fetchData(callback) {
  setTimeout(() => {
    const data = 'Server response: user data';
    callback(null, data);   // Node.js convention: (error, result)
  }, 1000);
}

// Pass a function as the callback argument
fetchData((err, result) => {
  if (err) { console.error(err); return; }
  console.log(result); // "Server response: user data" (after 1s)
});
💡

Error-first convention: In Node.js and older APIs, callbacks follow the pattern (error, result) — the first argument is always an error object (or null if success), the second is the result. Always check the error first!

😱 Callback Hell — The Pyramid of Doom

When you have sequential async operations where each one depends on the result of the previous one, callbacks nest inside each other. Each indentation level is another async dependency. This is called Callback Hell — and it's not just ugly, it's dangerous:

Why it's bad: Error handling must be duplicated at every level. Refactoring is nearly impossible. Stack traces become unreadable. Testing individual steps is painful. Code reviewers want to quit.

getUser(1, (err, user) => {
getOrders(user.id, (err, orders) => {
getOrderDetails(orders[0].id, (err, details) => {
getShipping(details.id, (err, shipping) => {
getTracking(shipping.id, (err, tracking) => {
// 😵 5 levels deep. Imagine adding error handling at each.
});
});
});
});
});
❌

Hard to read — indentation grows horizontally until you scroll

❌

Error handling must be repeated at every single nesting level

❌

Can't easily break into functions — each inner function needs outer data

🚀

Solution: Promises. Promises were invented specifically to flatten this pyramid into a linear chain. Instead of nesting, you chain with .then(). We'll see this next.

Section 04

Promises

A Promise is a JavaScript object that represents the eventual result of an asynchronous operation. Think of it as a placeholder — a receipt that says "this will have a value, or an error, some time in the future." You can attach handlers to it immediately, before the value even arrives.

🔑

Why Promises over callbacks: Promises are composable, chainable, and have standardized error handling. They were introduced in ES6 (2015) and are the foundation that async/await is built on. You cannot use async/await without Promises — they are the same system.

The Three States

Every Promise exists in exactly one of three states at any moment. Once it moves out of Pending, it cannot change again — this immutability is a core guarantee.

⏳
Pending
The initial state. The async operation is still in progress. Neither resolve nor reject has been called yet. The Promise is waiting.
✅
Fulfilled
resolve(value) was called. The operation succeeded. Attached .then() callbacks receive the value. This state is permanent.
❌
Rejected
reject(reason) was called (or an exception was thrown inside). The operation failed. Attached .catch() callbacks receive the error. Also permanent.
⚠️

Immutability matters: Once a Promise is fulfilled or rejected, calling resolve() or reject() again has zero effect. You cannot "undo" or "retry" a settled Promise. To retry, you create a new Promise.

Creating a Promise

You construct a Promise by passing an executor function to new Promise(). The executor receives two functions as arguments: resolve and reject. You call one of them when your async work is done.

Important: The executor function itself runs synchronously — immediately when you call new Promise(). Only the resolution is async.

js 
const myPromise = new Promise((resolve, reject) => {
  // ← This executor function runs RIGHT NOW, synchronously
  // It receives two control functions: resolve and reject

  setTimeout(() => {              // simulate async work
    const success = true;

    if (success) {
      resolve('✅ Data arrived!');  // → Fulfilled. .then() fires.
    } else {
      reject(new Error('❌ Server crashed')); // → Rejected. .catch() fires.
    }
  }, 1000);
});

// Attach handlers BEFORE the async work even completes — that's fine!
// The handlers are stored and called when the Promise settles.
myPromise
  .then(result => console.log(result))    // Fulfilled path
  .catch(error  => console.error(error)) // Rejected path
  .finally(() => console.log('Done'));   // Always runs

.then() · .catch() · .finally() — The Chain

Each .then() call returns a new Promise. Whatever you return inside a .then() becomes the resolved value of that new Promise, which is passed to the next .then(). This is how the chain stays flat instead of nesting. One single .catch() at the end is enough to handle errors from any step above it — the error propagates down the chain automatically.

1
getUserData(userId)
The originating Promise
This function returns a Promise that will eventually resolve with a user object { id, name, age }, or reject if the userId is invalid. This is the source of the chain.
Returns Promise
2
.then(user => { ... return user.id })
First handler — receives the user, returns id
The user argument here is the value passed to resolve() in the previous step. Whatever you return inside this .then() is automatically wrapped in a Promise and becomes the input to the next .then(). Here we extract just user.id and pass it forward.
Passes: user.id (number)
3
.then(id => { ... return `Profile #${id}` })
Second handler — receives id, builds a message
Now id is what was returned in the previous step. We don't need the user object anymore — it was already narrowed down. We build a string and return it. You can return a plain value (synchronous result) or another new Promise() (async chaining continues).
Passes: "Profile #1 loaded"
4
.then(message => { console.log(message) })
Third handler — receives the final message
This .then() returns nothing (implicitly undefined), which resolves to a fulfilled Promise with undefined. That's fine — we're at the end of the chain. The next step is .catch().
!
.catch(error => { console.error(error) })
Error handler — catches ANY rejection above
If any of steps 1–4 reject or throw an exception, the chain short-circuits. The rejection skips all remaining .then() handlers and lands here. One .catch() protects the entire chain. You can also re-throw from here if needed, and the error will propagate further.
Catches all upstream errors
∞
.finally(() => { hideSpinner() })
Cleanup handler — always runs, regardless of outcome
Runs whether the chain fulfilled or rejected. It receives no arguments — it doesn't know what the result or error was. It's purely for cleanup: hiding loading spinners, releasing resources, logging completion. Does not affect the chain's resolved/rejected value.
Success OR failure — always
js 
getUserData(1)
  .then(user => {
    console.log('User:', user.name);   // "Ali"
    return user.id;                    // passed to next .then()
  })
  .then(id => {
    console.log('ID:', id);            // 1
    return `Profile #${id} loaded`;
  })
  .then(msg => console.log(msg))      // "Profile #1 loaded"
  .catch(err => console.error(err))  // any error in steps 1–3
  .finally(() => hideSpinner());     // cleanup, always

Static Promise Methods

These are utility methods on the Promise constructor itself — not on a Promise instance. They let you work with multiple Promises at once.

Promise.all()
All must succeed
Runs ALL promises in parallel. Resolves with an array of all results — only when every single one resolves. If ANY one rejects, the whole thing rejects immediately and the other results are discarded. Use when you need every result and can't proceed without all of them.

Best for: loading all assets needed to render a page.
Promise.race()
First one wins
Settles (resolves OR rejects) with whichever Promise settles first. The others are ignored. This is how you implement timeouts: race your request against a Promise that rejects after N seconds.

Best for: abort strategy — take fastest data source, implement request timeouts.
Promise.allSettled()
Never rejects
Waits for ALL promises regardless of outcome. Returns an array of result objects with { status: 'fulfilled', value } or { status: 'rejected', reason }. You see every result — successes and failures — without the whole thing aborting.

Best for: batch operations where partial success is acceptable.
⚡ Try All Three Static Methods

Three promises: 300ms, 700ms, 500ms. all() waits for all three. One failure kills all.

Three promises at 100ms, 500ms, 1000ms. race() returns the first to finish.

One resolves, one rejects. allSettled() shows both outcomes — never throws.

❌ Wrong
// No .catch() — silent failure
fetchData()
  .then(d => process(d));
// If rejected → nothing happens!
// "Unhandled Promise Rejection"
// Node will crash. Browsers warn.
✅ Correct

  .then(d => process(d))
  .then(r => display(r))
  .catch(e => handleError(e))
  .finally(() => spinner(false));

Section 05

async / await

async/await is described as "syntactic sugar" — a cleaner syntax that compiles to Promise-based code. It doesn't replace Promises; it makes writing and reading them dramatically easier by letting async code look synchronous.

🔑

Under the hood: async function getUser() { return data; } is equivalent to function getUser() { return Promise.resolve(data); }. The JS engine transforms async/await into Promise chains behind the scenes. Knowing this helps you debug when something unexpected happens.

The Four Rules

Rule 1
async keyword
Place async before function. Works with all function forms: async function fn(){}, const fn = async () => {}, async fn(){} in a class. The function now always returns a Promise, regardless of what you return.
Rule 2
await keyword
Place await before any expression that returns a Promise. Execution inside the async function pauses here until the Promise settles. The resolved value is assigned to the variable. Other code outside this function continues normally.
Rule 3
Only inside async
await is only valid inside an async function. Using it at the top level gives a SyntaxError in classic scripts. Exception: ES modules (type="module") support top-level await.
Rule 4
try/catch for errors
When an awaited Promise rejects, it throws — which means try/catch works exactly as it does with synchronous errors. This replaces .catch() and feels far more natural for sequential async code.

Promise Chain vs async/await — Same thing, different look

📜 Promise .then() style
function loadProfile(id) {
  return fetch(`/api/users/${id}`)
    .then(res => {
      if (!res.ok) throw new Error(res.status);
      return res.json();
    })
    .then(user => {
      console.log(user.name);
      return fetch(`/api/orders/${user.id}`);
    })
    .then(res => res.json())
    .catch(err => console.error(err));
}
✨ async/await style
async function loadProfile(id) {
  try {
    const res  = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(res.status);
    const user = await res.json();

    console.log(user.name);

    const oRes   = await fetch(`/api/orders/${user.id}`);
    const orders = await oRes.json();
    return orders;
  } catch (err) {
    console.error(err);
  }
}
💡

Why it reads better: The async/await version reads top-to-bottom like synchronous code. Variables are in scope everywhere (no need to pass data via return values through the chain). Error handling is one try/catch block. Debugging shows clean stack traces. This is why async/await became the dominant style.

try/catch/finally — Complete Error Handling

js 
async function loadUserProfile(userId) {
  try {
    // ─────────── Step 1: Fetch user ───────────
    const userRes = await fetch(`/api/users/${userId}`);

    // fetch() itself only rejects on network failure, NOT on HTTP errors.
    // A 404 or 500 response still "succeeds" from fetch's perspective.
    // So we MUST manually check response.ok and throw if needed.
    if (!userRes.ok) {
      throw new Error(`HTTP Error: ${userRes.status} ${userRes.statusText}`);
    }

    // Parsing the body is also async — it streams the response data
    const user = await userRes.json();
    console.log('User:', user.name);

    // ─────────── Step 2: Fetch orders ───────────
    const ordersRes = await fetch(`/api/users/${userId}/orders`);
    const orders    = await ordersRes.json();

    return { user, orders };

  } catch (error) {
    // Catches: network failures, HTTP errors we throw, JSON parse errors,
    // or any exception thrown anywhere inside the try block.
    console.error('Something went wrong:', error.message);
    return null;

  } finally {
    // Runs AFTER try (if succeeded) or AFTER catch (if failed).
    // Use for cleanup that must happen no matter what.
    hideLoadingSpinner();
    console.log('Loading complete (success or error)');
  }
}

Sequential vs Parallel — A Critical Performance Difference

The most common async/await mistake is using await sequentially when the requests don't depend on each other. Each await pauses until that request completes before starting the next one — you're throwing away the benefit of async.

🐌 Sequential — Unnecessary waiting
async function loadData() {
  // Request 2 won't START until request 1 ENDS.
  // Request 3 won't START until request 2 ENDS.
  // Even though these three don't depend on each other!
  const users    = await fetchUsers();   // 1s
  const posts    = await fetchPosts();   // 1s
  const comments = await fetchComments(); // 1s
  // Total: 3 seconds 😴
}
🚀 Parallel — All start simultaneously
async function loadData() {
  // All three start at the exact same moment.
  // We await all of them together.
  const [users, posts, comments] =
    await Promise.all([
      fetchUsers(),
      fetchPosts(),
      fetchComments()
    ]);
  // Total: max(1s, 1s, 1s) = 1 second 🚀
}
Sequential
3 seconds total
Parallel
~1 second

Rule: if requests don't depend on each other → always use Promise.all(). Can be 3–10× faster depending on your API latency.

⚠️

When sequential IS correct: If request 2 needs data from request 1's response (e.g., you need the user's ID before fetching their orders), you must use sequential await. The order only matters when there's an actual data dependency.

Section 06

Fetch API & REST

The Fetch API is the modern, Promise-based way to make HTTP requests from JavaScript. It replaced the older XMLHttpRequest (XHR) and works perfectly with async/await. Understanding it means understanding HTTP itself.

HTTP Methods — What each one means

REST APIs are built around HTTP verbs. Each verb signals the intent of the operation to the server. Using the wrong verb is like saying "DELETE please" when you mean "GET".

GET

Read data. No body sent. Safe and idempotent — calling it 100 times has the same effect as calling it once. Fetch posts, read profile, list products.

POST

Create new data. Body contains the new resource. Not idempotent — calling it 3 times creates 3 records. Register user, submit form, create order.

PUT / PATCH

Update existing data. PUT replaces the whole resource; PATCH updates only specified fields. Edit profile, change password, update status.

DELETE

Remove data. Idempotent — deleting something that's already deleted is the same as deleting it once. Delete account, remove post, cancel subscription.

GET Request — Reading Data

The simplest fetch call. Two awaits are always needed: one for the response headers, one for the body. They're separate because the body streams asynchronously.

js 
async function getPosts() {
  // Step 1: Make the request. Await resolves when HEADERS arrive.
  // The body may still be streaming at this point!
  const response = await fetch(
    'https://jsonplaceholder.typicode.com/posts?_limit=5'
  );

  // Step 2: ALWAYS check status. fetch() does NOT throw on HTTP errors!
  // A 404 "Not Found" is still a "successful" response to fetch().
  // response.ok is true for status 200–299, false for everything else.
  if (!response.ok) {
    throw new Error(`HTTP Error: ${response.status} ${response.statusText}`);
  }

  // Step 3: Parse the body as JSON. This is also async — it reads
  // the full response stream and parses it. Never call both .json()
  // and .text() on the same response — you can only read the body once!
  const posts = await response.json();

  console.log(posts); // [{id:1, userId:1, title:'...', body:'...'}, ...]
  return posts;
}

POST Request — Sending Data

When sending data, you provide an options object as the second argument to fetch(). The body must be a string — you convert your JavaScript object to JSON with JSON.stringify(). The Content-Type header tells the server how to parse it.

js 
async function createPost(title, body) {
  const response = await fetch(
    'https://jsonplaceholder.typicode.com/posts',
    {
      method: 'POST',              // Use POST, not GET
      headers: {
        'Content-Type': 'application/json'  // Tell server: "I'm sending JSON"
        // Other common headers: 'Authorization': 'Bearer token123'
      },
      body: JSON.stringify({        // Convert JS object → JSON string
        title: title,               // fetch() body must be a string!
        body: body,
        userId: 1
      })
    }
  );

  // Server returns the created resource with its new ID (usually 201 Created)
  const newPost = await response.json();
  console.log('Created:', newPost); // { id: 101, title: '...', ... }
  return newPost;
}

The Response Object — What you get back

js 
const response = await fetch('https://api.example.com/data');

// ── Status information ──────────────────────────────────────────
response.status      // Number: 200, 201, 400, 401, 403, 404, 500...
response.ok          // Boolean: true if status 200-299, false otherwise
response.statusText  // String: "OK", "Not Found", "Internal Server Error"
response.headers     // Headers object: response.headers.get('Content-Type')

// ── Body parsing methods (each returns a Promise, pick ONE per response) ──
const json  = await response.json();   // JSON string → JavaScript object/array
const text  = await response.text();   // Raw text (HTML, XML, CSV...)
const blob  = await response.blob();   // Binary data (images, PDFs, files)

// ⚠️ You can ONLY read the body once. Calling .json() after .text()
// on the same response throws "body already used" error.

JSON.stringify() & JSON.parse() — The bridge between JS and the network

The network can only transport text. JSON is a text format that represents JavaScript data structures. You need to convert in both directions:

js 
// JS Object → JSON String (for SENDING data over the network)
const user = { name: 'Ali', age: 25, active: true };
const jsonStr = JSON.stringify(user);
console.log(jsonStr);         // '{"name":"Ali","age":25,"active":true}'
console.log(typeof jsonStr); // "string" — it's just text now

// JSON String → JS Object (for RECEIVING data from the network)
const parsed = JSON.parse(jsonStr);
console.log(parsed.name);         // "Ali"
console.log(typeof parsed.age); // "number" — types are restored!

// Note: response.json() does JSON.parse() for you internally

Managing UI States During Fetch

A complete fetch interaction has four possible UI states. Always handle all of them or your UI will be confusing for users:

js 
async function loadPosts() {
  // 1️⃣  LOADING — show a spinner immediately
  container.innerHTML = '<p>⏳ Loading...</p>';

  try {
    const res   = await fetch('/api/posts');
    if (!res.ok) throw new Error(`Server error: ${res.status}`);
    const posts = await res.json();

    // 2️⃣  EMPTY — server responded fine but there's no data
    if (posts.length === 0) {
      container.innerHTML = '<p>📭 No posts yet</p>';
      return;
    }

    // 3️⃣  SUCCESS — render the actual data
    container.innerHTML = posts
      .map(p => `<div class="post"><h3>${p.title}</h3><p>${p.body}</p></div>`)
      .join('');

  } catch (error) {
    // 4️⃣  ERROR — network failure, HTTP error, or JSON parse failure
    container.innerHTML = `<p>❌ ${error.message}</p>`;
  }
}

Promise Chain
fetch(url)
  .then(res => res.json())
  .then(data => use(data))
  .catch(err => handle(err))
  .finally(() => cleanup());
async/await
async function load() {
  try {
    const r = await fetch(url);
    if (!r.ok) throw new Error();
    return await r.json();
  } catch(e) { handle(e); }
  finally { cleanup(); }
}
Parallel Requests
const [a, b, c] =
  await Promise.all([
    fetch('/a').then(r=>r.json()),
    fetch('/b').then(r=>r.json()),
    fetch('/c').then(r=>r.json())
  ]);
