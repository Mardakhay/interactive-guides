01 — React Hook

useEffect

React's escape hatch for talking to the outside world — APIs, timers, the DOM, and more.

Every React component has one job: take some data, return some UI. That's it. Clean, predictable, pure.

But real applications need to do other things. They need to fetch data from a server, start a timer, listen to keyboard events, update the page title. These are called side effects — work that happens outside the render cycle.

useEffect is how you safely run side effects after React has updated the DOM. Think of it as React telling you: "I'm done rendering — you can go do your side stuff now."

🍽️
Restaurant Analogy: The render is making the food. A side effect is like placing the order to the kitchen — it happens alongside the main work, but separately. The customer sees the food (the UI), not all the kitchen work happening behind the scenes.
4Side Effect Types
3Dep Array Modes
1Rule: runs after render

What counts as a side effect?

🌐

Data Fetching

Calling APIs with fetch(), axios, or any async request to a server.

⏱️

Timers

setTimeout, setInterval — anything that runs code on a delay or repeatedly.

🎧

Event Listeners

Attaching listeners to window, document, or other DOM elements outside your component.

🗄️

Storage & DOM

Reading/writing localStorage, updating document.title, or direct DOM manipulation.

🔌

Subscriptions

WebSockets, pub/sub systems, Firebase listeners — any ongoing connection that needs to be cleaned up.

📊

Third-party libs

Initializing Chart.js, Google Maps, or any library that needs a DOM element to attach to.

Why can't I just fetch during render?

Posts.jsx broken 
function Posts() {
  const [posts, setPosts] = useState([]);

  // 💥 This runs on EVERY render
  // setPosts triggers a re-render
  // re-render calls fetch again... forever
  fetch('/api/posts')
    .then(r => r.json())
    .then(data => setPosts(data)); // ← INFINITE LOOP! 🔄

  return <div>{posts.length} posts</div>;
}
Posts.jsx correct 
function Posts() {
  const [posts, setPosts] = useState([]);

  useEffect(() => {
    // ✅ Runs ONCE after mount, never again
    fetch('/api/posts')
      .then(r => r.json())
      .then(data => setPosts(data));
  }, []); // ← empty array = "only run once"

  return <div>{posts.length} posts</div>;
}

useEffect syntax breakdown 
useEffect(() => {
  // ① SETUP: Your side effect code lives here
  //   - fetch data
  //   - subscribe to events
  //   - start a timer
  console.log('Effect ran!');

  // ② CLEANUP: Return a function to "undo" the effect
  //   This runs before the next effect, or when component unmounts
  return () => {
    console.log('Cleaning up...');
  };

}, [dependency1, dependency2]);
//  ↑ ③ DEPENDENCY ARRAY: Controls when the effect re-runs

The Dependency Array — The Most Confusing Part

The second argument to useEffect is an array that tells React when to re-run the effect. A lot of bugs come from getting this wrong.

useEffect(fn, [])

Empty Array

Runs once after the component first appears on screen. Perfect for initial data loading.

Like componentDidMount

useEffect(fn, [val])

With Dependencies

Runs after mount, then again whenever a value in the array changes.

Like componentDidUpdate

useEffect(fn)

No Array ⚠️

Runs after every single render. Almost never what you want — usually a bug.

Use very rarely

dependency-examples.jsx 
// ✅ Empty array — fetch once on mount
useEffect(() => {
  fetchUserProfile();
}, []);

// ✅ Dependency — re-fetch when userId changes
//   e.g., user navigates from /user/1 to /user/2
useEffect(() => {
  fetchUser(userId);
}, [userId]); // ← re-runs whenever userId changes

// ✅ Multiple deps — re-run when either changes
useEffect(() => {
  fetchPosts(page, category);
}, [page, category]);

// ⚠️  No array — runs after every render (almost always wrong)
useEffect(() => {
  console.log('runs after EVERY render...');
});

Real Example: Fetching Data with Loading & Error States

Any time you fetch data, you need to handle three states: loading (waiting for response), error (something went wrong), and success (data arrived). Never skip the first two.

PostsPage.tsx production pattern 
interface Post { id: number; title: string; body: string; }

function PostsPage() {
  const [posts, setPosts] = useState<Post[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const fetchPosts = async () => {
    setLoading(true);
    setError(null);
    try {
      const res = await fetch('https://jsonplaceholder.typicode.com/posts?_limit=10');
      if (!res.ok) throw new Error(`HTTP error: ${res.status}`);
      const data = await res.json();
      setPosts(data);
    } catch (err) {
      setError(err instanceof Error ? err.message : 'Unknown error');
    } finally {
      setLoading(false); // ← always runs, even on error!
    }
  };

  useEffect(() => { fetchPosts(); }, []); // ← call async fn inside effect

  // Render based on state — ORDER matters!
  if (loading) return <p>⏳ Loading...</p>;
  if (error) return <div>❌ {error} <button onClick={fetchPosts}>Retry</button></div>;
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}
⚠️
Important: Never pass an async function directly to useEffect: useEffect(async () => {}) is wrong. Instead, define your async function inside the effect and call it immediately.

Cleanup Functions — Preventing Memory Leaks

When a component unmounts (disappears from the page), any ongoing effects should be stopped. If you don't clean up, you can end up with timers firing after a component is gone, or worse — updating state on a component that no longer exists (a memory leak).

Timer cleanup 
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);
  }, 1000);

  // Stop timer when component leaves
  return () => clearInterval(id);
}, []);
Event listener cleanup 
useEffect(() => {
  const handler = (e: KeyboardEvent) => {
    if (e.key === 'Escape') setOpen(false);
  };

  window.addEventListener('keydown', handler);

  // Remove listener when component leaves
  return () => {
    window.removeEventListener('keydown', handler);
  };
}, []);

02 — Pattern

Component
Composition

Building big UIs from small, focused pieces — the React superpower that makes code reusable and maintainable.

Composition is simply combining small components to build bigger ones. Each component does one job really well, and you snap them together like LEGO bricks.

This is different from inheritance (what OOP uses). Instead of "a UserCard IS-A Card," we think "a UserCard HAS-A Avatar and HAS-A Username." It's the composing of capabilities, not inheriting them.

The payoff: small components are easy to test, easy to reuse, and easy to change without breaking everything else.

🧱
The LEGO Principle: You wouldn't carve a LEGO castle from one block of plastic. You'd build it from small, interchangeable pieces that click together. Component composition is exactly this — small, focused, reusable pieces that snap together into something complex.
composition-example.jsx good 
// Small, single-purpose components
function Avatar({ src, size = 40 }) {
  return <img src={src} width={size} height={size} style={{ borderRadius: '50%' }} />;
}

function Badge({ label, color }) {
  return <span style={{ background: color, borderRadius: '4px', padding: '2px 8px' }}>{label}</span>;
}

// Composed into a bigger component
function UserCard({ user }) {
  return (
    <div className="card">
      <Avatar src={user.avatar} />   {/* ← reusable */}
      <h3>{user.name}</h3>
      <Badge label={user.role} color="#3b82f6" />  {/* ← reusable */}
      <p>{user.email}</p>
    </div>
  );
}

// Can reuse Avatar and Badge anywhere else too!
function CommentItem({ comment }) {
  return (
    <div>
      <Avatar src={comment.author.avatar} size={24} />  {/* same Avatar! */}
      <p>{comment.text}</p>
    </div>
  );
}

The children Prop

The children prop is React's special reserved prop. It automatically contains whatever you put between the opening and closing tags of a component. This makes it perfect for building wrapper components like layouts, modals, and cards — that hold anything inside them.

Provides: border, shadow, padding, title

Card.tsx — the wrapper 
function Card({ children, title }: {
  children: React.ReactNode;
  title: string;
}) {
  return (
    <div className="card">
      <h3>{title}</h3>
      <div>
        {children} ← magic here
      </div>
    </div>
  );
}

Prop Drilling — The Problem Composition Solves

Prop drilling happens when you need to pass data through multiple layers of components that don't actually use that data — they just pass it along. It's like playing telephone: each person has to repeat the message even though they don't care about it.

App has user ✅
passes user ↓
→
Layout doesn't use it ❌
passes user ↓
→
Sidebar doesn't use it ❌
passes user ↓
→
UserMenu finally uses it ✅

Layout & Sidebar are forced to accept props they don't care about 😤

prop-drilling.jsx messy 
function App() {
  const [user] = useState(userData);
  return <Layout user={user} />;
}

function Layout({ user }) {
  // Layout doesn't use user AT ALL
  return <Sidebar user={user} />;
}

function Sidebar({ user }) {
  // Sidebar doesn't use user either!
  return <UserMenu user={user} />;
}

function UserMenu({ user }) {
  return <p>{user.name}</p>; // ← finally used
}
composition-solution.jsx clean 
function App() {
  const [user] = useState(userData);
  return (
    <Layout>                         {/* no user prop! */}
      <Sidebar>                       {/* no user prop! */}
        <UserMenu user={user} />      {/* passed directly! */}
      </Sidebar>
    </Layout>
  );
}

function Layout({ children }) {
  return <div className="layout">{children}</div>;
}

function Sidebar({ children }) {
  return <aside>{children}</aside>;
}

function UserMenu({ user }) {
  return <p>{user.name}</p>; // clean & direct
}
💡
Rule of thumb: 2–3 levels of prop passing is totally fine. 4+ levels? Start thinking about composition or Context API. The goal is: components only know about data they actually need.

Useful Composition Patterns

📐

Layout Pattern

Create page shells with slots for content. Header/main/footer don't change; your page content slots in.

function Page({ children }) {
  return (
    <><Header/>
      <main>{children}</main>
    <Footer/></>
  );
}
🎯

Container / Presentational

Split logic from display. "Smart" containers fetch and manage state; "dumb" components just render props.

// Smart — fetches
function PostsContainer() {
  const [posts] = useFetch(...);
  return <PostsList posts={posts} />;
}
// Dumb — just displays
function PostsList({ posts }) {
  return <ul>...{posts}</ul>;
}
🔌

Slot Pattern

Like children, but multiple named slots. Think of it as named regions a component can accept content into.

function Dialog({ header, body, footer }) {
  return (
    <div>
      <div>{header}</div>
      <div>{body}</div>
      <div>{footer}</div>
    </div>
  );
}
03 — Core Concept

Lists &
Keys

Rendering arrays efficiently — and why React needs that little key prop so badly.

In React, you render lists using JavaScript's .map() — it transforms an array of data into an array of JSX elements. This is one of the most common patterns you'll write.

But there's a catch: React needs a way to track each item in the list. When the list changes (items added, removed, reordered), React needs to know which item is which. That's what the key prop is for.

🔑
What's a key, really? Think of keys like nametags at a party. If everyone wears a nametag, you can quickly spot who arrived, who left, and who just moved seats — without re-reading everyone's face from scratch. React uses keys the same way to efficiently update only what changed.
UserList.tsx basic pattern 
interface User {
  id: number;
  name: string;
  email: string;
}

function UserList({ users }: { users: User[] }) {
  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>               {/* ← key is required! */}
          <strong>{user.name}</strong>
          <span>{user.email}</span>
        </li>
      ))}
    </ul>
  );
}

Why Keys Actually Matter

WITHOUT keys — React has to re-render everything when the list changes:

re-renderAlice
re-renderBob
re-renderCarol
re-renderDave (new)

WITH keys — React only processes what actually changed:

skipAlice ✓
skipBob ✓
skipCarol ✓
createDave 🆕
🚫
Don't use index as key — when items are added, removed, or reordered, the index of each item changes. React gets confused and can show stale UI, lose input values, or animate incorrectly. 
// ❌ Index changes when list changes
items.map((item, index) =>
  <Item key={index} />
)
✅
Always use a stable, unique ID — database IDs are perfect. They never change for the same item, even if the item moves in the list. 
// ✅ ID is stable regardless of order
items.map(item =>
  <Item key={item.id} />
)

Filter → Sort → Map: The Power Chain

You'll often need to filter, sort, AND render a list. Chain .filter(), .sort(), and .map() together. Always filter first (discard what you don't need), sort second (order what's left), map last (turn data into UI).

ProductList.tsx derived state pattern 
function ProductList() {
  const [products] = useState(allProducts);
  const [search, setSearch] = useState('');
  const [sortBy, setSortBy] = useState('name');

  // ✅ Derived state — no extra useState needed!
  // React re-calculates this on every render automatically
  const displayProducts = products
    .filter(p => p.name.toLowerCase().includes(search.toLowerCase()))
    .sort((a, b) => sortBy === 'price'
      ? a.price - b.price
      : a.name.localeCompare(b.name))
    .map(p => <ProductCard key={p.id} product={p} />);

  return (
    <>
      <input
        value={search}
        onChange={e => setSearch(e.target.value)}
        placeholder="Search products..."
      />
      <select onChange={e => setSortBy(e.target.value)}>
        <option value="name">Sort by Name</option>
        <option value="price">Sort by Price</option>
      </select>
      {displayProducts}
    </>
  );
}

useState vs useEffect — Know the Difference

Aspect useState useEffect
Purpose Stores and manages data inside your component Handles work outside the render cycle (side effects)
When it runs You call setState() — triggers a re-render After the component renders (React controls this)
Causes re-render? Yes — that's the whole point No — but the effects inside it might (via setState)
Use for... Input values, counters, toggle states, fetched data API calls, timers, event listeners, subscriptions
Mental model "What data should my component remember?" "What should happen after rendering?"
💬 Quick summary: useState = "what to remember" | useEffect = "what to do after rendering"
